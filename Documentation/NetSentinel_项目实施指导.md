# NetSentinel 项目实施指导

> 本文用于统一项目目标、交付范围、分工和进度。算法、数据库、接口、页面及部署的具体实现分别写入设计文档，不在此展开。

## 一、项目概况

**项目名称：** NetSentinel——可扩展安全规则引擎与日志关联分析平台

**项目目标：** 开发一个面向实验室、小型服务器和教学环境的安全日志分析系统。用户导入获得授权的 Nginx、Linux SSH 日志后，系统根据检测规则识别可疑行为，生成可解释的告警，并支持人工处置和审计追溯。

本项目的主要工作是**自主开发 Go 规则引擎**，Web 管理平台用于完成日志导入、规则管理、分析和告警处置。项目不是单纯的后台管理系统，也不以页面数量或代码行数作为完成标准。

| 项目 | 约定 |
|---|---|
| 团队 | 4 人，角色可兼任 |
| 后端与核心引擎 | Go |
| 前端 | React + TypeScript，使用 Web 页面交互 |
| 数据存储 | SQLite |
| 部署 | 单机 Docker Compose，配套自动化构建、测试及部署流程 |
| 协作平台 | GitHub：Issues、Pull Requests、Projects、Actions、Releases |
| 开发方式 | 需求基线约束下的增量迭代开发 |

## 二、系统要完成的工作

### 2.1 业务流程

**导入日志 → 解析并标准化 → 选择规则 → 运行分析 → 生成告警及证据 → 人工处置 → 审计与通知。**

系统以离线日志分析为主。相同数据集使用相同版本的规则重新分析，应得到一致的逻辑告警结果，不因重复执行而产生重复告警，也不应覆盖已有的人工处置状态。

### 2.2 用户角色

| 角色 | 主要工作 |
|---|---|
| 管理员（admin） | 管理用户和权限、导入日志、配置和发布规则、设置通知 |
| 安全分析员（analyst） | 启动分析、查询告警、核对证据、认领和处置告警 |
| 审计员（auditor） | 只读查看分析历史、规则版本、告警和操作记录 |

权限必须由后端校验，不能只依靠前端隐藏按钮。

### 2.3 核心功能

| 模块 | 必须实现的内容 |
|---|---|
| 日志管理 | 导入 Nginx、Linux SSH 日志；查看解析结果、异常记录和数据集 |
| 规则管理 | 创建、校验、测试、启停和发布规则；保留规则版本 |
| 规则引擎 | 独立执行 Count、Distinct、Sequence 三类检测，输出命中原因与证据 |
| 分析任务 | 选择数据集和规则运行分析；查看进度、结果及失败原因；支持重复分析 |
| 告警处置 | 筛选告警、查看原始证据和命中解释、认领、标记误报、关闭及备注 |
| 权限与审计 | 三种角色的权限控制，以及关键操作的审计记录 |
| 通知与指标 | 飞书机器人高危告警通知；显示基础处理耗时、吞吐量及命中统计 |

三类核心检测能力分别用于：统计一段时间内的事件次数（Count）、统计不同对象的数量（Distinct）、识别按一定顺序发生的事件（Sequence）。典型演示包括 SSH 多次登录失败、HTTP 路径枚举以及 SSH 多次失败后成功登录。

### 2.4 暂不纳入核心版本

受限 DSL 文本编译器、复杂事件关联、跨源 Join、乱序事件处理、检查点恢复和并行加速均为**选做增强**。只有在核心版本完成、测试通过且课程资料齐全后再安排。

不开发网络抓包、实时流量阻断、自动封禁、漏洞利用、主机常驻 Agent、分布式集群或 CLI/TUI 产品界面。规则命中只表示存在可疑线索，不代表已确认发生入侵。

## 三、版本安排

项目分成三个可运行增量。每个版本都要有对应的需求、代码、测试、PR 记录和 Release，不接受仅完成独立模块但无法演示的版本。

| 版本 | 目标 | 验收重点 |
|---|---|---|
| **v0.1：数据与基础检测** | 完成日志导入、事件标准化、Count 检测和最小告警展示 | 能导入样例日志并产生有原始证据的告警 |
| **v0.2：规则引擎核心** | 加入 Distinct、Sequence、规则版本、告警去重与解释 | 能演示路径枚举及 SSH 失败后成功；重复分析不增加逻辑告警 |
| **v0.3：完整产品** | 完成三角色权限、Web 工作台、人工处置、审计、飞书通知、测试及部署 | 从登录到告警处置的完整业务流程可独立运行 |

**v0.3 为课程核心交付版本。** 增强功能不能影响 v0.3 的完成时间、质量和答辩准备。

## 四、四人分工

| 成员 | 主要负责内容 | 课程过程责任 |
|---|---|---|
| **A** | 日志解析与统一事件、规则配置和校验；后续可参与 DSL | 组长、需求调研、SRS、计划与变更管理 |
| **B** | Count、Distinct、Sequence 及规则引擎正确性测试 | 架构与设计、分析模型、核心构件设计 |
| **C** | 数据存储、告警幂等、权限、后端服务、飞书通知 | GitHub/CI、配置管理、部署和运行保障 |
| **D** | React Web、操作流程和前后端联调 | 测试与验收、性能验证、AI 使用报告 |

这是一份初始分工，实际任务通过 Issue 分配。A、D 在主要工作稳定后参与引擎测试和性能验证；B、C 的大型任务应拆分为可单独评审的 PR。每个成员都应理解所负责模块的需求、设计、实现与测试，而不是只完成一类文档或页面。

## 五、课程进度与检查点

第 9—16 周以需求、建模、设计和 DevOps 检查为主；其后推进编码、测试、发布和答辩。具体日期以教师安排为准。

| 周次 | 当周重点 | 必须形成的成果 |
|---|---|---|
| 第 9 周 | 组队、立项、调研准备 | 教师审核选题；仓库、选题 Issue、章程草稿、调研计划 |
| 第 10 周 | 真人访谈与用户故事 | 访谈纪要、需求调研报告、带验收标准的用户故事 |
| 第 11 周 | 需求规约 | 用例图、SRS v1.0、非功能需求、需求追溯矩阵及评审记录 |
| 第 12 周 | 分析建模草稿 | CRC 卡、分析类图、活动图、状态图、顺序图源文件 |
| 第 13 周 | 分析模型评审 | 需求分析规约定稿、正式评审记录、更新的追溯矩阵 |
| 第 14 周 | 概要设计 | 架构、数据库、接口契约、设计决策记录（ADR） |
| 第 15 周 | 详细设计 | 至少两个核心构件设计、部署图、设计评审、迭代与测试计划 |
| 第 16 周 | DevOps 检查 | CI 通过、首个可运行版本 Tag、测试用例库初版 |

第 16 周以后按 v0.1、v0.2、v0.3 继续交付。项目至少完成**两轮有计划、构造、测试、评审和回顾记录的迭代**，并在两轮之间交换一次结对或评审对象。

## 六、软件工程与 GitHub 要求

1. **需求先确认。** 安排真实干系人访谈，教师审核立项；项目计划中的功能和分析类只是候选项。完成调研后才发布正式 SRS 基线。
2. **规模要满足课程要求。** 最终至少 20 个用例（其中至少 2 个非功能用例）、15 个分析类、3 种用户角色、1 个外部集成点、3 个可交付增量和 1 个受管理的技术风险。当前计划提供 22 个功能用例、2 个非功能用例和 18 个分析类候选，正式版本须经调研与评审确认。
3. **模型必须完整。** 至少细化 3 个用例并绘制活动图；提交 CRC 卡、分析类图、至少 2 张关键类状态图及必要的顺序图。概要设计覆盖架构、数据库、接口和部署；详细设计覆盖至少 2 个核心构件。
4. **过程要可追溯。** 按 `需求 → 用例/模型 → 设计 → 测试 → 发布` 建立追溯关系。变更以 Issue 发起，经评审批准后更新相关文档，不能只在聊天中决定。
5. **所有工作走 GitHub。** 采用 `Issue → 分支 → PR → 人工 Review → CI → Merge` 流程；保护 `main` 分支，禁止直接推送。模型、文档、代码和缺陷修复都要有对应记录。
6. **持续验证与发布。** Actions 自动构建和测试，失败时禁止合并；增量通过 Milestone 管理并创建 Release。按课程要求配置可复现的自动部署或经认可的等效流程。
7. **落实个人贡献。** 每人至少主讲一次课堂讲解、至少 10 个被合并的有效 PR，参加答辩问答。全组至少完成两次正式代码抽样评审，期末提交 0—10 分贡献互评。
8. **AI 使用必须登记。** AI 可用于草稿、辅助编码和测试，但真人访谈、需求确认、架构决策、验收放行和 PR 审核由人负责。保留实际修改或否决 AI 产出的案例，不上传敏感日志、个人信息或密钥。

## 七、测试与验收

测试不只检查页面能否打开，还要验证规则结果是否正确、同样输入是否可复现、权限是否有效。

| 检查项目 | 验收内容 |
|---|---|
| 规则正确性 | Count、Distinct、Sequence 正例、反例、时间边界与不同用户/IP 的隔离 |
| 结果一致性 | 相同数据集和规则版本重复分析时，逻辑告警一致、没有重复记录，不覆盖处置结果 |
| 规则版本 | 修改规则后产生新版本；历史告警保留对应版本和证据 |
| 权限与审计 | 不同角色的操作范围符合规定，越权接口调用被拒绝，关键操作可追溯 |
| 外部通知 | 飞书高危告警能发送；失败或超时可检查投递状态，使用 Mock 验证异常场景 |
| 性能 | **10,000 条事件**完成端到端验证；**100,000 条事件**完成引擎与完整链路基准测试，记录环境、耗时、吞吐和结果正确性 |
| 部署 | 可根据仓库说明部署、运行和复现演示；CI 与发布记录可查 |

性能达标阈值由需求评审后确定；**不能把尚未测试的目标写成实际性能结果**。提交单元测试、集成测试和从用户角度编写的验收测试，核心模块声明覆盖率，保留测试输入、原始结果和缺陷处理记录。

## 九、最终演示与完成标准

**答辩安排：** 每组 20 分钟，其中系统演示 12 分钟、问答 8 分钟，每位成员至少回答一问。

建议按以下顺序演示：

1. 使用三种角色登录，展示权限差异。
2. 导入授权的 SSH 和 Nginx 样例日志，查看解析结果。
3. 选择规则运行分析，演示 SSH 失败后成功和 HTTP 路径枚举。
4. 查看告警命中原因、原始证据及人工处置记录。
5. 对同一数据集重复分析，验证告警去重和结果一致性。
6. 查看审计、飞书通知状态和性能测试结果。

项目完成以 **v0.3 业务闭环运行正常、核心规则引擎通过测试、三次增量可追溯、课程资料完整并能现场复现** 为准。代码量和选做功能数量不是替代验收的依据。

## 十、开始实施前需确认的事项

- 教师是否批准选题、核心范围与过程模型。
- 真人调研对象、访谈安排及可使用的授权/脱敏日志。
- 四名成员的实际分工、课堂主讲顺序与每周负责人。
- 经评审的 SRS、非功能验收阈值及最终答辩日期。

以上事项完成后更新项目章程与计划，所有变更通过 GitHub 留痕。
