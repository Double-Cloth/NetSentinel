# NetSentinel 功能与需求规格

版本 v0.1，状态为待调研及评审的需求候选。本文定义业务结果与操作约束，算法遵循独立规则引擎详细设计，接口和持久化遵循前后端与数据实现设计。

## 1. 干系人与业务约束

真实调研建议覆盖一名实验室服务器管理员、一名承担日志排查任务的使用者和一名教师或审计检查者，分别记录现有流程、日志样例、可接受误报、处置职责、数据保存和性能期望。访谈由成员实际开展，记录时间、授权、问题、原始回答、需求结论及确认人。

系统面向同一组织内的共享日志空间。admin 负责数据与规则管理，analyst 执行检测与处置，auditor 只读检查。日志须来自授权环境，展示和导出以实验脱敏样本为基础。内置规则给出可疑线索及其证据，人工根据上下文确认和处置。

离线数据集一旦进入 ready 状态，其文件、解析器版本、解析参数和事件内容固定。规则一旦发布，其内容、归一化规则与语义版本固定。分析任务创建时保存数据集、规则版本集合和引擎版本，后续规则启停与新版本发布仅影响新任务的默认选择。

## 4. 三个细化用例

### 4.1 UC-04 导入数据集

前置条件为 admin 已登录且拥有授权文件。触发为用户确认预览并开始导入。成功后数据集 ready，全部有效事件稳定排序，原始行可追溯，失败行单独保存。

1. Web 提交文件、格式、source_host、timezone，以及 SSH 传统时间格式需要的 year。
2. 服务验证权限、大小、格式和参数，流式写入受控目录，生成摘要。
3. 服务创建 importing 数据集，固定解析器版本、参数与上传者，返回 202。
4. 后台逐行解析，写入事件与错误行，计算稳定事件 ID。
5. 按 `(event_time_us, line_no)` 形成排序序号，计算有效事件摘要。
6. 成功则以事务将数据集切换 ready，写入审计并展示统计。

失败路径覆盖文件超限、无有效事件、解析参数缺失、磁盘写入失败、解析取消与进程中断。错误行可容忍并保留，参数错误和系统故障使数据集 failed。重复上传相同字节、格式和参数时返回已有有效数据集，failed 导入可显式重新创建导入尝试，事件内容按成功数据集固定。

活动图设计应包含“校验→写文件→解析循环→错误分支→排序→事务发布→展示”，外加全流程系统错误出口。

### 4.2 UC-13 启动并完成分析

前置条件为 admin/analyst 登录、数据集 ready、规则版本可用且来源兼容。成功后任务 succeeded，Finding、告警、任务关联、证据和 Outbox 作为完整结果可查询。

1. 用户选择数据集、规则及显式版本，提交 `Idempotency-Key`。
2. 服务验证并保存不可变快照，创建 queued 任务，重复请求返回同一任务。
3. Worker 领取任务，按固定排序读取事件并调用独立引擎。
4. 引擎输出 Finding 和指标，服务将结果写入任务专属 staging。
5. 引擎全部成功后，服务在事务中以指纹合并正式告警、证据、任务关联及通知记录。
6. 任务切换 succeeded，返回新增告警数、复用告警数、总命中数及耗时。

规则在执行期间发布新版本时，任务继续使用已保存快照。输入排序错误、资源预算超限或存储失败时，任务 failed 并保存阶段化错误，staging 不进入正式列表。服务中断后的运行任务标记 failed，用户可按原快照重跑。

活动图应含权限校验、幂等分支、队列、引擎失败、事务回滚和成功发布。必要顺序图覆盖 Web、API、Worker、Engine、Repository 与 Outbox。

### 4.3 UC-19 处置告警

前置条件为告警 open 或 acknowledged，用户为 admin 或当前认领的 analyst。成功后当前状态、处置历史和审计一致。

1. 用户查看证据及命中解释，先认领 open 告警。
2. Web 获取告警 `row_version`，提交动作及必填理由。
3. 服务验证角色、当前负责人、状态转换和版本。
4. 使用条件更新并在同一事务中写处置历史、审计。
5. 前端刷新状态和时间线，保留当前筛选上下文。

另一用户已修改时返回 409 并提示刷新查看新状态。告警已关闭时拒绝再次变更终态，备注可由 admin 或原负责人追加。网络超时可用操作幂等键重新查询原结果，避免重复历史。重复分析沿用已存在告警的状态和负责人。

活动图包含版本冲突、无权限、理由缺失、提交失败与成功路径。

## 5. 关键状态与业务不变量

| 对象 | 状态转换 | 不变量 |
| --- | --- | --- |
| 数据集 | importing → ready / failed | ready 数据、解析配置和摘要固定，失败数据集不可启动分析 |
| 规则 | draft 的修订不断增加，publish 创建新 RuleVersion，enabled 控制默认选择 | 发布版本不可覆盖，编辑始终作用于草稿 |
| 分析任务 | queued → running → committing → succeeded，活动状态可 → failed | 每次执行只有一个终态，正式结果仅在 succeeded 的原子发布中出现 |
| 沙箱任务 | queued → running → succeeded / failed | 结果短期保留在沙箱命名空间，业务告警与通知均无写入 |
| 告警 | open → acknowledged → closed / false_positive | 认领者与处置历史一致，终态保留，重跑不更新处置字段 |
| 通知 | pending → sending → sent / retry_wait / dead | 同一逻辑告警与渠道最多一条自动通知，重试共享同一投递记录 |

Sequence 的内部阶段与业务任务状态分别描述，规则详细设计给出内部状态的转换条件。

## 6. 非功能预算与测量口径

以下为待需求评审的候选阈值，测试报告填写实际结果和通过结论。

| 维度 | 候选目标 | 测量方法 |
| --- | --- | --- |
| 确定性 | 相同数据集、规则版本及引擎语义版本，逻辑 Finding 完全一致 | 对规范化排序后的指纹、指标值与证据 ID 做比较，排除运行时间字段 |
| 幂等性 | 顺序/并发重跑均无重复逻辑告警，已处置状态保持 | 多次重跑与并发请求，比较唯一指纹、处置历史及自动 Outbox 数量 |
| 10,000 条链路 | 从导入请求开始至任务结果可查询，候选预算 30 秒以内 | 4 vCPU、8 GiB 内存、SSD、本地容器，包含上传、解析、排序、排队、引擎和提交，排除人工停留 |
| 100,000 条引擎 | 8 条规则，预排序事件，候选预算 10 秒以内、引擎进程峰值 RSS 512 MiB 以内 | 预热 1 次、测量 5 次，输出中位数和最慢值，核对结果 |
| 100,000 条完整链路 | 候选预算 120 秒以内、后端峰值 RSS 1 GiB 以内 | 从导入至结果可查询，分别报告解析、排序、读取、引擎、提交和总耗时 |
| 常规查询 | 100,000 事件与 10,000 告警下，列表查询 p95 500 ms 以内 | 本机 API 连续 100 次并记录筛选条件，包含数据库耗时 |
| 权限 | 权限矩阵全部写接口越权拒绝，审计可追溯 | 直接调用 API 验证 401/403，前端按钮控制同步检查 |
| 可靠性 | 失败任务无正式部分结果，成功任务可追溯原始证据 | 注入解析、引擎、提交、重启和通知故障 |
| 部署 | 干净环境按说明启动并通过固定夹具烟测 | 保留镜像、配置、迁移、版本与完整执行记录 |

系统的引擎输入以事件数计量，文件导入以原始行数计量。全链路吞吐使用有效事件数除以全链路秒数，引擎吞吐使用引擎处理事件数除以引擎墙钟秒数，同时记录规则数、总匹配数、输出数与错误行数。

## 7. 需求变更与 AI 声明
