# NetSentinel 独立规则引擎详细设计

版本 v0.1，状态为待评审设计。本文为核心语义规格，候选规则阈值需结合真实样本确认。时间窗口、证据、版本和失败行为一经评审，作为实现及测试共同依据。

## 1. 独立性与构件边界

引擎计划放在 `engine/` 独立 Go module，能够仅通过该目录执行单元测试、基准和内存事件示例。引擎只依赖 Go 标准库，拥有统一事件、规则、编译计划、Finding、运行指标及错误类型。业务后端通过模块依赖调用，负责日志解析、排序、数据库、任务、用户权限、处置和通知。

| 引擎内部 | 职责 | 依赖限制 |
| --- | --- | --- |
| `event` | 事件字段类型、字段访问、稳定顺序检查 | 标准库 |
| `rule` | JSON 解码、结构校验、类型检查、规范化、Compile | event、标准库 |
| `predicate` | 纯函数式过滤表达式执行 | event、标准库 |
| `runtime` | 按来源分发、分组、预算、取消、指标 | event、rule、标准库 |
| `detector` | Count、Distinct、Sequence 状态机 | 编译计划、标准库 |
| `finding` | 证据快照、原因结构、逻辑指纹 | event、rule、标准库 |

模块依赖方向为 `backend → engine`，前端通过 HTTP 使用后端。引擎入口对事件迭代器和 Finding 接收器编程，测试可使用 slice 输入和内存接收器，后端实现 SQLite 读取及 staging 写入适配器。新增检测器需扩展规则类型、编译器和检测器工厂，并提供独立语义与测试向量。

### 1.1 外部调用契约

建议的 Go API 形态如下，最终字段定义在编码前形成稳定接口。

```go
type EventIterator interface {
    Next(ctx context.Context) (Event, bool, error)
}

type FindingSink interface {
    Write(ctx context.Context, finding Finding) error
}

func Compile(snapshot RuleVersionSnapshot) (CompiledRule, error)

func Run(
    ctx context.Context,
    input EventIterator,
    rules []CompiledRule,
    options RunOptions,
    sink FindingSink,
) (RunStats, error)
```

RuleVersionSnapshot 包含 RuleSpec、rule_version、spec_hash 与 engine_semantics_version，Compile 重新计算摘要并检查版本兼容性。正式分析要求 rule_version 大于零，沙箱使用 version=0 的临时快照并由后端隔离保存。一个 Run 仅接受每个 rule_id 的一个版本，重复规则 ID 显式拒绝。

`Next` 返回的 bool 表示是否存在事件，迭代器关闭由调用者负责。编译结果不可变，可被不同任务共享，每次 Run 单独创建全部检测状态。Run 同步执行，输入错误、取消、配额超限或接收器失败均返回错误。失败前已经写入 sink 的 Finding 由调用方保存在未发布 staging，业务后端在 Run 成功后统一提交。

引擎以输入迭代顺序输出，单事件内按 `rule_id` 排序执行规则。单个 Run 对应一个 dataset_id，逻辑比较使用排序后的指纹及证据，RunStats 中实际耗时单独记录。输入中 dataset_id 变化、重复的 event_id、非递增 event_index 或时间回退均报 `INPUT_ORDER_INVALID`。重复 ID 校验使用本次 Run 的已见集合，其内存计入运行预算。

## 2. 统一事件模型

### 2.1 字段字典

| 字段 | 类型 | 含义与归一化 |
| --- | --- | --- |
| `schema_version` | integer | 统一事件结构版本，初始为 1 |
| `event_id` | string | 解析阶段生成的稳定 SHA-256 摘要 |
| `event_index` | integer | 数据集内从 1 开始的排序序号 |
| `dataset_id` | string | 不可变数据集标识，由适配层提供 |
| `event_time_us` | int64 | UTC Unix 微秒，计算使用该字段 |
| `source` | enum | `ssh` 或 `nginx` |
| `source_host` | string | 目标服务器标识，优先使用可信导入配置，必要时核对日志主机 |
| `kind` | enum | `ssh.auth_failed`、`ssh.auth_success`、`http.access` |
| `src_ip` | IP string | 使用 `net/netip` 解析并规范化，IPv4-mapped IPv6 统一为 IPv4 |
| `user.name` | optional string | SSH 登录目标用户，大小写保持原样，缺失与空值分开 |
| `ssh.invalid_user` | optional boolean | 仅由 `Failed ... for invalid user ...` 标记产生 |
| `ssh.auth_method` | optional enum | `password`、`publickey`、`keyboard-interactive` 等已支持模板 |
| `http.method` | optional string | 大写 HTTP 方法 |
| `http.path` | optional string | 从请求目标提取的原始路径，去查询与片段，保留大小写、转义和尾斜杠 |
| `http.status` | optional integer | HTTP 状态码 |
| `http.bytes_sent` | optional int64 | 非负响应字节数，原始 `-` 视为缺失 |
| `raw_ref` | struct | 文件标识、原始行号、原始行摘要，可回查原始文本 |

SSH 检测事件要求时间、主机、来源 IP 与用户名可解析。Nginx 检测事件要求时间、主机、IP、方法、路径及状态码可解析。其他合法 SSH 行，如会话关闭和断开消息，计入 `ignored_lines`，对应支持模板的失败/成功行解析错误计入 `error_lines`，导入界面分别显示。

`http.path` 的路径与编码归一化固定在 parser 版本，初始语义保留百分号转义及重复斜杠，例如 `/a?x=1` 和 `/a?x=2` 均为 `/a`，`/%61` 与 `/a` 为不同路径。敏感路径规则基于该字面语义，编码变体的覆盖作为后续规则或归一化版本演进处理。

### 2.2 时间与稳定顺序

单文件数据集按 `(event_time_us ASC, line_no ASC)` 排序并分配 event_index。同一微秒的事件由原始行号决定前后。引擎遵循该全序，Sequence 的“随后”意味着 event_index 更大，允许时间戳相同的两行组成先后关系。

RFC3339 时间使用自身时区，Nginx combined 使用日志中的数值偏移。缺少年份与时区的 SSH RFC3164 输入需要显式 year 与 timezone，timezone 可为数值偏移或 IANA 名称。IANA 地区遇到 DST 不存在或重复的本地时间时记录 TIME_AMBIGUOUS，要求改用明确数值偏移后重新导入。首版一个文件只对应一个指定年份，跨年文件要求按年份切分后导入，系统预览提示该限制。解析及排序一次完成，检测阶段输入已经有序。

### 2.3 稳定身份

数据集身份由文件字节摘要、解析器版本和规范化解析参数共同确定。解析参数包括来源、格式、主机、时区、年份及字段映射，采用固定键序的规范化 JSON。

本文 canonical_json 统一采用 UTF-8、无额外空白、对象键按字典序、数组保留业务顺序、整数十进制无前导零、布尔与 null 使用 JSON 字面值，字符串遵循 JSON 转义并关闭 HTML 特殊转义。in/not_in 集合在规范化前去重排序，group_by 与 stages 保留数组顺序。规范化实现及哈希向量作为共享契约由单元测试固定。

`event_id = SHA256(canonical_json([dataset_digest, line_no, raw_line_hash]))`。

原始行去掉行结束符后计算 raw_line_hash，同样文本在不同原始行仍产生不同事件。重复上传复用同一成功数据集，因此相同日志重跑保持事件身份。数据集范围进入告警指纹，不同数据集即使部分内容重叠，也按各自分析结果保存，首版不做跨数据集相同攻击合并。

## 3. 规则配置与编译

### 3.1 规则公共结构

规则使用结构化 JSON，schema_version 为 1。rule_id 稳定，发布版本号由规则管理服务分配。以下为 R-001 的完整配置示例。

```json
{
  "schema_version": 1,
  "rule_id": "R-001",
  "name": "SSH 同账户连续窗口内多次认证失败",
  "description": "同一来源在同一主机上对同一账户产生至少 5 次认证失败",
  "source": "ssh",
  "type": "count",
  "severity": "medium",
  "group_by": ["source_host", "src_ip", "user.name"],
  "window_seconds": 300,
  "where": {
    "all": [
      {"field": "kind", "op": "eq", "value": "ssh.auth_failed"}
    ]
  },
  "threshold": 5
}
```

RuleVersion 包装层包含 `version`、`spec_hash`、`published_by`、`published_at`、`engine_semantics_version`。enabled 属于规则管理记录，不进入不可变版本内容。API 任务创建请求明确传入 rule_id 与 version，服务加载快照后调用 Compile。

### 3.2 表达式、字段和缺失值

表达式节点为 `all`、`any` 或一个字段比较，节点三者互斥。all/any 子项必须非空，深度最多 4 层、总节点最多 64。首版提供以下操作符。

| 操作符 | 字段与值类型 | 语义 |
| --- | --- | --- |
| `eq`、`neq` | string、integer、boolean，同类型 value | 精确相等或不等 |
| `in`、`not_in` | string/integer，对应同类型非空数组，最多 100 项 | 集合包含或排除 |
| `gt`、`gte`、`lt`、`lte` | integer，integer value | 数值比较 |
| `prefix` | string，string value | 大小写敏感前缀 |
| `regex` | string，string value | Go regexp 匹配，建议规则显式使用锚点控制范围 |
| `exists` | 任意字段，boolean value | 比较字段是否存在 |

字段缺失时，除 exists 外全部比较返回 false，包括 neq 和 not_in。空字符串为存在的值，但 user.name/http.path 的空字符串无法作为有效分组或 Distinct 值。规则不可读取任意原始文本或动态 JSON 字段，编译器使用字段白名单及来源适用性检查。

正则在 Compile 时预编译，长度最多 1,024 字节，采用 Go regexp 支持的语法。Go 官方文档说明该实现匹配时间随输入长度线性增长，规则预算还需限制模式、字段长度和总匹配次数。[Go regexp 官方文档](https://pkg.go.dev/regexp)

### 3.3 分组键与类型

group_by 为 1—4 个无重复字段，支持 `source_host`、`src_ip`、`user.name`、`http.method`、`http.path` 和 `http.status`，须与 source 兼容。数组顺序即分组元组顺序，采用带类型的规范化 JSON 数组编码，例如 `["srv-a","192.0.2.10","root"]`。避免字符串分隔符造成键碰撞。

缺少任意分组字段时，该事件对该规则记 `skipped_missing_group` 并跳过。过滤失败、分组缺失、Distinct 字段缺失分别计数。每个 Run 的 `(rule_id, version, group_key)` 有独立状态，规则间、账户间、主机间及不同任务间完全隔离。

### 3.4 类型专属配置

| 类型 | 必需字段 | 限制 |
| --- | --- | --- |
| `count` | where、threshold | threshold 为 1—10,000 的整数 |
| `distinct` | where、threshold、distinct_field | 同上，distinct_field 是该 source 支持的 string 或 integer 字段 |
| `sequence` | 恰好两个 stages | 第一步 `min_count` 为 1—10,000，第二步 min_count 固定为 1，两步各有 where |

sequence 初版支持“第一类事件至少 k 次，然后第二类事件一次”的两阶段顺序。两个 stage_id 固定为 `start`、`finish`。sequence 根节点不接受 where、threshold、distinct_field，count/distinct 不接受 stages。所有 window_seconds 为 1—86,400 的整数，severity 为 low/medium/high/critical。

### 3.5 编译步骤与错误

1. 严格 JSON 解码，拒绝未知字段、重复对象键、浮点阈值及超大请求。
2. 检查结构版本、rule_id、名称长度、来源、类型、字段必需及互斥关系。
3. 递归检查谓词节点、字段类型、操作符和值类型，预编译正则与集合。
4. 检查分组、窗口、阈值、阶段及运行预算的兼容性。
5. 按固定字段顺序规范化配置，集合去重并按值排序，生成 spec_hash。
6. 输出不可变 CompiledRule，包含来源路由、字段访问器、谓词、检测参数与元数据。

错误统一为 code、path、message，例如 `RULE_VALUE_TYPE` 和 `/where/all/0/value`。结构错误使用 `RULE_SCHEMA_INVALID`，未知字段为 `RULE_FIELD_UNKNOWN`，正则错误为 `RULE_REGEX_INVALID`，配置超限为 `RULE_LIMIT_EXCEEDED`。编译无系统 I/O、副作用及数据库访问。

## 4. 三类检测的共同语义

### 4.1 时间窗口

窗口按事件时间计算，对当前事件时间 t 与窗口 W，保留区间为 `[t-W, t]`，左右均闭合。过期条件严格为 `old.event_time_us < t-W`。计算使用 int64 微秒，窗口秒数经过范围检查后转换，输入时间也做可表示范围检查。

核心版本读取已排序数据集。每条规则先判断 source，再执行谓词，匹配事件进入所属分组。Count/Distinct 只在匹配事件到达时评估阈值。过期回收可在相关事件到达时执行，跨长时间间隙通过惰性过期或过期最小堆清理，无须墙钟定时器。

### 4.2 Count/Distinct 告警周期

采用阈值进入告警语义。每个分组持有 armed 标志，初始为 true。处理一条匹配事件时先过期清理，若清理后的指标低于 threshold，则设 armed=true。随后加入当前事件，若指标达到阈值且 armed=true，则输出一个 Finding 并将 armed=false。

该告警代表触发时刻的窗口快照。持续达到阈值期间的后续匹配事件更新检测状态，首个 Finding 的证据保持固定。只有下一次过期清理使指标降到阈值以下，才允许产生下一次告警。这个规则同时用于 Count 和 Distinct。

例子为 threshold=3、W=60 秒，事件发生在 0、10、20、30 秒时，仅在 20 秒输出。若下一条在 91 秒，先移除所有小于 31 秒的事件，重新武装，然后从新窗口累计。窗口阈值下降发生在事件时间推进的过程中，具体 Finding 始终由当前匹配事件触发。

### 4.3 冷却与证据约束

首版使用上述阈值周期控制重复告警，规则结构不增加额外 cooldown 参数。告警证据保存触发窗口内全部相关 event_id 及顺序，界面分页展示。容量超限时任务显式失败，不静默删除影响正确性的证据。

### 4.4 输入路由与空闲回收

按 source 建立规则索引，减少无关谓词执行。每个 detector 的活跃分组登记下一过期时间，在处理新输入时可通过最小堆回收已完全失效的空分组。堆节点携带 generation，忽略旧版本节点，避免更新后的状态被旧节点误删。Count/Distinct 只在队列为空时删除组，Sequence 在失败队列为空时删除组。

若先达到预算且待清理状态可能过期，先按当前事件时间统一清理，再判断超限。不同实现优化必须通过相同金标准验证，逻辑输出保持一致。

## 5. Count 详细设计

状态为每组的时间有序双端队列 `events` 和 armed。队列元素保存 event_id、event_time_us、event_index 与 raw_ref，当前次数等于队列长度。

处理步骤为来源与谓词检查、组键提取、移除窗口左侧过期事件、根据旧计数重新武装、压入当前事件、检查新计数、必要时创建 Finding 快照。Count 使用队列头索引避免每次移动整个 slice，按需压缩底层数组。

R-001 在同一主机、IP 与用户下 300 秒出现至少 5 次失败。成功登录对 Count 状态无清空作用，Count 的统计对象为失败事件，成功后的失败仍按滑动窗口计算。Sequence 单独负责成功导致阶段重置的语义。

Count 输出解释字段包含 threshold、actual_count、window_start_us、window_end_us、first_evidence_time_us、last_evidence_time_us、group_values 和 trigger_event_id。window_start_us 为 `t-W`，第一条证据时间可以晚于该值。

复杂度为每个匹配事件入队、出队各一次，均摊 O(1)，Finding 证据复制按实际证据数量 E 计 O(E)，总空间为窗口内有效引用及输出证据。

## 6. Distinct 详细设计

状态为事件队列、值引用计数 `map[TypedValue]int` 和 armed。distinct_field 缺失或为空时跳过并计数，同一个值的重复事件仍加入队列，以便正确维护最后一个副本过期的时刻。

每次过期时，对对应值引用计数减一，减到零才删除 map 键。当前不同值数量为 map 的长度。加入当前事件后若数量越过阈值则输出 Finding，并保存窗口内全部匹配事件及按规范值排序的 unique_values。

例如值序列为 `/a@0`、`/a@50`、`/b@55`，W=60。在 t=61 清理后，`/a@0` 过期但 `/a@50` 仍在，/a 的引用数从 2 变 1，distinct_count 仍包含 /a。直接使用集合删除过期值会破坏这个结果。

Distinct 证据包含重复值的全部窗口事件，解释增加 distinct_field、actual_distinct 和 unique_values。单次匹配更新均摊 O(1)，值集合空间为 O(U)，事件队列空间为 O(M)，证据复制额外按输出量计。

## 7. Sequence 详细设计

### 7.1 两阶段契约

Sequence 维护每组的 `start_events` 队列，表示最近 W 内尚未被 finish 消费的 start 事件。第一阶段达到 k 后进入 waiting_finish，finish 必须出现在所有已选 start 之后，且最早所选 start 至 finish 的时间差不超过 W。

处理当前事件时先使过期 start 出队，然后按以下次序执行。

1. 若当前事件满足 finish 谓词，检查队列长度是否至少 k。
2. 满足 k 则输出一个 Finding，证据为当前窗口中全部 start 加当前 finish，stage 分别标注 start 和 finish。
3. 无论是否达到 k，finish 都清空该组 start 队列，回到 idle。
4. 若当前事件不满足 finish 且满足 start，则压入队列，更新阶段。
5. 两类谓词都不满足时，保留经清理后的状态。

若一条事件同时满足两个 stage，finish 优先，该事件仅作为 finish 处理。事件不会在同一条 Sequence 中兼作两步，start 不会跨 finish 重用。任意多个相邻成功仅可能第一个消费此前失败。不同 Sequence 规则可独立使用同一事件。

### 7.2 阶段与边界

| 状态 | 条件 | 下一事件与动作 |
| --- | --- | --- |
| idle | 队列为空 | start 后进入 accumulating，k=1 时直接 waiting_finish |
| accumulating | 0 < 队列长度 < k | start 增加，达到 k 后 waiting_finish，finish 清空 |
| waiting_finish | 队列长度 ≥ k | finish 输出并清空，start 可继续积累，过期后可能回到 accumulating/idle |

R-003 的 k=5、W=300 秒。失败在 0、60、120、180、240 秒，成功在 300 秒命中。成功在 301 秒时，0 秒失败过期，剩 4 次，结果为无命中。相同时间的失败与成功按原始行序处理，成功在前时不能使用后面的失败。

R-003 根配置如下。

```json
{
  "schema_version": 1,
  "rule_id": "R-003",
  "name": "SSH 多次失败后认证成功",
  "description": "同一来源对同一主机同一账户在 300 秒内至少失败 5 次后成功",
  "source": "ssh",
  "type": "sequence",
  "severity": "high",
  "group_by": ["source_host", "src_ip", "user.name"],
  "window_seconds": 300,
  "stages": [
    {
      "stage_id": "start",
      "min_count": 5,
      "where": {"all": [{"field": "kind", "op": "eq", "value": "ssh.auth_failed"}]}
    },
    {
      "stage_id": "finish",
      "min_count": 1,
      "where": {"all": [{"field": "kind", "op": "eq", "value": "ssh.auth_success"}]}
    }
  ]
}
```

输出解释包括阶段名称、最小次数、实际失败次数、成功事件、窗口与有序证据。每个 start 事件入队、出队至多一次，均摊 O(1)，输出复制为 O(E)。首版该受限序列可用确定性状态机实现，任意多分支 NFA 留作增强候选。

## 8. 八条内置候选检测规则

所有规则均基于 schema_version=1，窗口采用 `[t-W,t]`。Count/Distinct 使用阈值周期，Sequence 使用 finish 消费。规则初始发布版本拟为 1，实际发布时间和批准记录由团队生成。主机记为 source_host，来源记为 src_ip。

| ID | 规则名称 | 类型与分组 | 精确谓词 | 参数与级别 |
| --- | --- | --- | --- | --- |
| R-001 | SSH 同账户多次认证失败 | Count，主机+来源+user.name | kind eq `ssh.auth_failed` | W=300 秒，threshold=5，medium |
| R-002 | HTTP 404 路径枚举 | Distinct，主机+来源 | kind eq `http.access` AND http.status eq 404 | distinct_field=http.path，W=60 秒，threshold=20，medium |
| R-003 | SSH 多次失败后成功 | Sequence，主机+来源+user.name | start 为 kind eq `ssh.auth_failed`，finish 为 kind eq `ssh.auth_success` | k=5，W=300 秒，high |
| R-004 | SSH 多账户失败尝试 | Distinct，主机+来源 | kind eq `ssh.auth_failed` | distinct_field=user.name，W=600 秒，threshold=5，high |
| R-005 | SSH 无效用户密集尝试 | Count，主机+来源 | kind eq `ssh.auth_failed` AND ssh.invalid_user eq true | W=300 秒，threshold=10，medium |
| R-006 | HTTP 敏感路径访问 | Count，主机+来源 | kind eq `http.access` AND http.path in `["/.env","/.git/config","/wp-login.php","/phpmyadmin/","/phpmyadmin/index.php"]` | W=60 秒，threshold=1，high，状态码不限 |
| R-007 | HTTP 服务端错误密集 | Count，主机 | kind eq `http.access` AND http.status gte 500 AND http.status lte 599 | W=60 秒，threshold=20，medium |
| R-008 | HTTP 拒绝访问路径探测 | Distinct，主机+来源 | kind eq `http.access` AND http.status in `[401,403]` | distinct_field=http.path，W=120 秒，threshold=10，medium |

R-002 的完整结构如下，其余规则按本表和公共配置生成版本化 JSON 夹具。

```json
{
  "schema_version": 1,
  "rule_id": "R-002",
  "name": "HTTP 404 路径枚举",
  "description": "同一来源在同一主机 60 秒内访问至少 20 个不同且返回 404 的路径",
  "source": "nginx",
  "type": "distinct",
  "severity": "medium",
  "group_by": ["source_host", "src_ip"],
  "window_seconds": 60,
  "where": {
    "all": [
      {"field": "kind", "op": "eq", "value": "http.access"},
      {"field": "http.status", "op": "eq", "value": 404}
    ]
  },
  "distinct_field": "http.path",
  "threshold": 20
}
```

### 8.1 逐条样例与限制

| 规则 | 正例 | 反例及人工核查要点 |
| --- | --- | --- |
| R-001 | 同主机/IP/root 于 0、60、120、180、240 秒失败，在 240 秒触发 | 分成 root 3 次、admin 2 次各不触发，用户输错密码可形成误报 |
| R-002 | 同主机/IP 在 60 秒内请求 `/probe/01` 到 `/probe/20` 且全部 404 | 同路径换 20 个 query 仅一个不同路径，合法爬虫可能触发 |
| R-003 | 5 次失败后同 IP/账户成功，首尾不超 300 秒 | 成功来自不同 IP 或不同账户不触发，排查是否为本人登录重试 |
| R-004 | 同主机/IP 在 600 秒内失败用户名 u1—u5 | 同用户名失败多次只计 1，共享跳板出口需结合上下文判断 |
| R-005 | 同主机/IP 在 300 秒内 10 条显式 invalid user 失败 | 只有独立 `Invalid user` 行时计为忽略，不与随后 Failed 行重复计数 |
| R-006 | 请求 `/.env` 即可触发，200/403/404 均符合 | `/.env.bak`、`/%2eenv` 不符合当前字面列表，同窗口持续访问仅首条触发 |
| R-007 | 同主机 60 秒内来自多 IP 的 20 条 5xx | 499、600 均不纳入，服务故障与恶意行为需结合其他证据判断 |
| R-008 | 同主机/IP 120 秒内 10 个不同路径返回 401 或 403 | 9 个不同路径或其他状态不触发，权限配置变化可能导致误报 |

规则启停、阈值调整与误报处理通过版本发布和人工处置记录保留依据。白名单、抑制配置和自动风险评分在本版范围内均不增加隐含检测语义，需求确认后可单独设计增强版本。

## 9. Finding、解释与逻辑指纹

### 9.1 Finding 结构

| 字段 | 内容 |
| --- | --- |
| identity | dataset_id、rule_id、rule_version、spec_hash、engine_semantics_version |
| grouping | 有序 group_fields 与带类型 group_values |
| time | window_start_us、window_end_us、trigger_time_us |
| trigger | trigger_event_id、trigger_event_index |
| metric | detection_type、actual_count/actual_distinct、threshold 或阶段计数 |
| evidence | 按 event_index 排序的 event_id、raw_ref、stage_id，可选 unique_values |
| reason | 可机器读取的解释参数与固定 reason_code |
| fingerprint | 规范化逻辑身份的 SHA-256 |

Count 的 reason_code 为 `COUNT_THRESHOLD_ENTERED`，Distinct 为 `DISTINCT_THRESHOLD_ENTERED`，Sequence 为 `SEQUENCE_COMPLETED`。展示文案由服务或前端根据固定字段生成，数值和证据可独立验证。

### 9.2 指纹组成

```text
fingerprint = SHA256(canonical_json([
  "finding-v1",
  dataset_id,
  rule_id,
  rule_version,
  spec_hash,
  engine_semantics_version,
  group_values,
  trigger_event_id
]))
```

同一规则同一分组最多在一个 trigger_event 生成一个 Finding。指纹排除 task_id、运行时间、负责人及处置状态。相同快照重跑输出相同指纹，新规则版本形成独立告警。代码修复若改变逻辑结果，提升 engine_semantics_version，并经评审说明历史重跑影响。

证据、指标与指纹对应的不可变内容建立 result_digest。正式落库时如果相同指纹已经存在但 result_digest 不同，则报 `RESULT_INCONSISTENT` 并回滚，防止未提升语义版本的行为变化被静默覆盖。构建提交号与镜像版本单独保存在任务中，便于诊断。

### 9.3 引擎与业务持久化分工

引擎负责生成正确、稳定的 Finding。服务通过 `alerts.fingerprint UNIQUE` 去重，重跑只添加 task_alerts 关联和任务统计。现有告警的 status、assignee、note、row_version 与历史始终沿用，证据保持对应快照。高危通知仅在新逻辑告警创建时进入 Outbox。

## 10. 资源、错误与指标

### 10.1 待实测的资源预算

| 项目 | 初始候选上限 | 超限行为 |
| --- | --- | --- |
| 单次 Run 规则数 | 100 | 拒绝启动 |
| 单次 Run 输入事件数 | 1,000,000 | 超限显式失败，已见 ID 集合受该上限约束 |
| 活跃 `(rule,group)` 数 | 20,000 | 先过期清理，仍超限则任务失败 |
| 全规则缓冲事件引用总数 | 200,000 | 显式 `ENGINE_RESOURCE_LIMIT` |
| 检测状态保留字符串累计字节 | 64 MiB | 分配前检查，超限显式失败，覆盖长路径及高基数值 |
| 单次 Finding 数 | 50,000 | 停止并标记任务失败 |
| 累计输出证据引用数 | 1,000,000 | 停止并标记任务失败 |
| 字段字符串长度 | 8 KiB | 解析或编译阶段拒绝对应非法输入 |
| 单次任务墙钟时间 | 后端候选 120 秒，可按评审调参 | ctx 取消，标记阶段和 `TASK_TIMEOUT` |

累计引用按每条规则各自引用计数，保留字符串字节按实际持有的 ID、分组和值内容计数，同一存储对象只计一次。数据共享优化另行验证。预算进入任务快照和测试环境信息，相同快照若资源不足可失败，成功输出必须符合完整语义。引擎与完整链路性能预算参考需求规格及测试方案。

### 10.2 运行指标

RunStats 记录 input_events、每规则 evaluated_events、matched_events、skipped_missing_group、skipped_missing_distinct、findings、peak_groups、peak_buffered_refs、evidence_refs 和 engine_elapsed。来源无关事件只进入输入总数，不进入该规则 evaluated_events。

Sequence 匹配任一 stage 的事件计入 matched_events 一次，finish 优先。Count/Distinct 的 where 通过后计入 matched_events，缺失分组或 distinct 时再记录对应 skipped。窗口内当前状态、最终 Finding 数与扫描匹配数分开统计。

### 10.3 错误传播与取消

错误包含 code、phase、rule_id（适用时）、event_id（适用时）与安全消息。原始日志只通过有权限的证据查询接口访问。Compile 错误属于规则配置，输入顺序错误属于适配契约，预算和取消属于运行错误，sink 失败属于存储边界。

每批输入及证据复制循环检查 ctx。Run 失败后清理内存状态，服务清理 staging 并保留失败记录。首版重启后按完整快照重新执行，全部状态由输入重建。

## 11. 实现与评审顺序

1. A/B 共同冻结字段与样本，手算 R-001、R-002、R-003 边界结果。
2. 实现严格解码、编译器、谓词与带类型分组键，建立错误路径夹具。
3. 实现 Count 及阈值周期，用真实入口 Run 验证证据和取消。
4. 实现 Distinct 引用计数与 Sequence 消费语义，加入缺失字段、同时间、分组隔离与过期用例。
5. 提取固定规则夹具、参考实现和独立基准，验证重复运行及乱序拒绝。
6. 与 C 集成 staging、指纹去重和状态保留，演练失败后的完整重跑。
7. 正式抽样评审算法与状态回收，使用实际基准决定优化，记录语义兼容结论。

核心构件评审需由负责人逐步解释每个状态如何建立、过期、触发、消费和释放，并能将测试结果追溯到具体规则条款。
