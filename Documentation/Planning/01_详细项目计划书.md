# NetSentinel 详细项目计划书

文档版本 v0.2，修订日期 2026-11-13，状态为待评审规划。编制依据为项目实施指导、课程要求及配套需求、引擎、前后端和测试设计。A、B、C、D 为待替换的成员代号。本版由 Codex 辅助重写，按项目成果和验收条件组织推进。

## 1. 项目目标与执行基线

### 1.1 业务目标

为实验室管理员和安全分析员提供离线日志检测工作流。用户导入授权日志，系统标准化为事件，由独立引擎运行明确版本的检测规则，保存告警及原始证据，通过人工认领、标记误报、关闭、备注形成处置闭环，并以审计和飞书通知支持追溯。

核心研发资源优先投入事件语义、规则校验、三类检测、确定性、状态隔离、证据构建和引擎测试。管理页面围绕这些能力组织，验收覆盖从原始文件到人工处置的完整流程。

### 1.2 交付范围

| 维度 | v0.3 核心交付边界 |
| --- | --- |
| 技术栈 | Go 独立规则引擎与后端、React + TypeScript Web、SQLite、单机 Docker Compose |
| 输入 | UTF-8 明文 Nginx combined、明确模板的 Nginx JSON、Linux SSH RFC3164/RFC3339 文本 |
| 执行 | 单机离线数据集，导入时排序，事件时间驱动，单任务串行运行 |
| 检测 | Count、Distinct、两阶段 Sequence，内置 8 条候选规则，可通过结构化配置创建同类型规则 |
| 规则治理 | 草稿、校验、沙箱测试、发布不可变版本、启停、版本查询 |
| 输出 | 告警、命中解释、完整事件引用、分析历史、运行指标 |
| 产品流程 | admin、analyst、auditor 三角色登录、导入、分析、告警处置、审计、飞书通知 |
| 质量 | 正确性、幂等、权限、恢复与故障、端到端验证、性能基准及部署复现 |

受限 DSL、任意多阶段关联、跨源 Join、流式乱序、水位线、检查点恢复和并行加速列为增强候选，进入条件为 v0.3 核心验收通过、课程资料齐全且团队确认剩余容量。网络抓包、自动封禁、漏洞利用、常驻 Agent、分布式集群和 CLI/TUI 产品界面遵循实施指导中的范围约束。

### 1.3 过程模型与决策责任

采用需求基线约束下的增量迭代。先确认业务与事件、规则契约，用 Count 完成第一条纵向链路，再验证 Distinct 与 Sequence 的状态行为，随后完善处置、通知与部署。每个增量均经历计划、构造、测试、评审、回顾，前一轮缺陷和风险结论进入下一轮计划。

三类检测可逐步交付，日志格式与时间边界需要样本验证，四人团队需要尽早集成，因此各轮均以可运行成果为目标。需求确认由真实干系人与 A 负责，架构由 B、C 提议并由团队签字，验收标准与放行由测试负责人和项目负责人组织人工确认。

### 2.3 进度记录与阶段切换

每个阶段开始时，A 组织确认目标、任务范围、负责人、可用人时和验收证据，C 将阶段目标映射到 GitHub Milestone 或关联 Issue。阶段目标有明确的交付结果后，再将任务分配到成员。

任务状态使用 Backlog、Ready、In Progress、In Review、Done。Ready 需要依赖满足、输入明确且具备验收标准。Done 需要需求或设计关联、可审阅产物、验证记录、人工 Review 和合并记录。受阻任务保留当前状态，另行登记阻塞原因、责任人和解除条件。

阶段评审由 A 汇总任务完成情况，D 汇总测试与缺陷，B/C 核对设计和运行风险。评审结论记录通过、补正后复核或重新规划，并附对应证据。未满足出口条件的关键项继续修复，后续阶段可提前开展已满足依赖的任务。

进度报告记录已验收工作包、进行中任务、阻塞项、剩余人时、风险和下一步行动。任务完成率按已验收任务数与当前基线任务总数计算，并同时列出关键路径状态。阶段完成以出口条件通过为准。

教师检查与答辩日期作为外部交付约束登记。每次收到安排后核对剩余容量和关键路径，必要时调整任务分工、拆分交付或申请范围变更。

## 4. 分阶段执行计划

### 4.1 阶段一，立项确认与协作准备

**阶段目标**为确认项目价值、成员责任、真实干系人和工作方式，形成可开展调研的输入。

**入口条件**为项目候选目标和课程要求已整理，成员可参与立项讨论。

1. A 汇总项目背景、业务目标、范围约束与增量过程选型理由，组织教师选题审核和成员确认。
2. A/D 确定管理员、日志排查使用者及教师或审计检查者等访谈对象，准备问题、纪要模板和样本授权记录。
3. C 核对仓库权限、分支保护、Issue/PR 模板和基础 CI，建立 Projects 及三个产品增量 Milestone。
4. 全员确认 A/B/C/D 的实际对应人员、模块交接方式和课堂主讲安排，D 建立 AI 使用台账与贡献记录。

**交付成果**包括项目章程、选题 Issue、成员责任表、调研计划、样本来源记录、初始风险清单和协作任务。

**出口条件**为选题与分工经人工确认，访谈对象和调研任务落实，仓库具备任务、评审与检查入口。尚待确认事项登记到责任人及对应任务。

### 4.2 阶段二，真实调研与需求基线

**阶段目标**为将候选能力转化为可确认、可测试、可追溯的需求。

**入口条件**为立项通过，干系人和样本获取方式明确。

1. A/D 开展真人访谈，核实日志来源、现有排查流程、误报处理、权限分工、数据保存和部署条件，保留真实回答及确认记录。
2. A 使用授权样本验证 Nginx/SSH 格式、时间字段和脱敏要求，记录格式差异与输入限制。
3. A 逐条复核 22 个功能用例、2 个非功能用例及三角色权限，为用户故事补充 Given/When/Then 验收标准。
4. D 将需求关联到测试场景，确认 10,000 条完整链路验证和 100,000 条双基准的测量口径，并组织非功能预算确认。
5. A 组织 SRS 正式评审，处理问题并建立申请、影响分析、评审、批准、生效的变更通道，发布 `srs-v1.0.0` 需求基线。

**交付成果**包括真实访谈纪要、调研报告、用户故事 Issues、SRS、用例图、权限矩阵、需求追溯矩阵和正式评审记录。

**出口条件**为核心业务流程与异常路径明确，需求来源、验收条件和负责人可追溯，范围及非功能预算已确认，基线版本可查询。

### 4.3 阶段三，分析建模与设计基线

**阶段目标**为明确模块边界、运行语义和协作契约，验证影响实现的关键技术风险。

**入口条件**为需求基线可用，授权或确定性合成样本可用于设计验证。

1. B/A 建立 CRC 卡、分析类图和必要顺序图，细化 UC-04、UC-13、UC-19 的活动图，完成任务与告警两张关键状态图。以 18 个候选分析类为起点核对职责与协作，正式模型至少包含 15 个分析类。
2. A/B 冻结事件字段、时间精度、稳定排序、规则配置、窗口边界、Sequence 消费、Finding、证据引用、错误及语义版本契约。
3. C/D 明确数据库约束、任务快照、幂等、结果原子提交、后端权限、API 类型和页面状态，确定前后端交接夹具。
4. B/C 用小规模原型验证窗口边界、同时间排序、高基数状态回收、SQLite 写竞争和发布事务，记录输入、结果与设计调整。
5. B/C 完成概要设计与至少两个核心构件详细设计，覆盖独立引擎及解析/任务提交构件，补齐部署图与 ADR。D 同步建立测试用例库和增量验收清单。
6. C/D 准备模块构建、依赖锁定、迁移与 CI 接入，确认干净环境的启动方式。各份正式规约经人工评审后记录版本和结论。

**交付成果**包括 `models/` 图源文件、分析规约、架构与接口契约、数据库及部署设计、核心构件详细设计、ADR、风险实验记录和测试计划。

**出口条件**为需求到模型及设计的关联完整，四方确认共同契约，关键风险具备验证结论或明确处置任务，各成员可据契约独立实施并联调。

### 4.4 阶段四，v0.1 最小业务链路

**阶段目标**为完成从 Web 导入日志到查看 Count 告警及原始证据的首次可运行交付。

**入口条件**为事件、规则和接口契约通过评审，测试输入及预期结果确定，基础工程可开始构建。

1. C/D 接入 Go/Web 构建、SQLite 初始迁移、基础登录、健康检查和 CI，使各模块可启动。
2. A/C 完成 Nginx/SSH 预览、导入、标准化、失败行保存、稳定排序及数据集查询，建立事件到原始行的引用。
3. B/A 完成规则结构与类型校验、谓词、分组键、Count 和证据解释，经真实 `Run` 入口验证阈值、窗口和状态隔离。
4. A/C/D 完成 Count 规则草稿与校验入口，为首个分析提供固定的已发布规则版本和任务快照。v0.2 继续完善发布、启停和历史管理。
5. C/D 接通异步任务、进度、结果保存、告警列表和详情，用 R-001 串联导入、分析与原始证据查看。
6. D 组织解析、引擎与链路测试，C 提供 Compose 启动和基础烟测，A 组织评审、回顾与 `v0.1.0` 发布。

## 6. 协作、评审与配置管理

### 6.1 任务推进与反馈

成员开始任务前核对输入、依赖和验收标准，完成可运行切片或遇到阻塞时更新 Issue。A 在阶段启动、集成和评审节点检查剩余工作量及关键路径，D 同步检查缺陷和证据完整性。

每个增量至少安排一次中途集成，验证已完成模块之间的真实接口。增量收口预留约 20% 容量用于测试、修复、正式评审和回顾，实际分配按风险调整。每轮保留计划、实际完成项、缺陷、测试结果、偏差原因与下一轮行动。

v0.1 结对或评审建议 A↔B、C↔D，v0.2 调整为 A↔D、B↔C，v0.3 再交叉抽样，落实至少一次轮换。首次正式抽样评审覆盖 v0.2 引擎与幂等，第二次覆盖 v0.3 权限与通知，记录问题、修复 PR 和复核结论。

### 6.2 仓库与分支流程

远端仓库为 `Double-Cloth/NetSentinel`，默认集成分支为 `main`。截至本次修订，远端 `main-protection` 规则集处于 `disabled` 状态，`main` 当前无生效的分支保护规则。C 在协作准备阶段负责落实保护启用并核验实际效果。

项目协作要求为至少一名其他成员人工批准、处理完全部评审讨论并通过 `CI 结果` 检查后合并，同时禁止直接推送、删除和强制推送 `main`。保护启用前，各成员仍按上述要求执行。

按 `Issue → 工作分支 → PR → 人工 Review → CI → Merge` 推进。功能、修复、文档和配置分支沿用 `feat/<issue>-<topic>`、`fix/<issue>-<topic>`、`docs/<issue>-<topic>`、`chore/<issue>-<topic>`。提交说明写明变更意图，PR 关联需求、设计、验证记录及对应 Issue。

原始资料初始化和规划草稿的历史提交按实际记录保留。后续文档、模型、代码与缺陷修复纳入同一协作流程，每张模型图使用独立 PR。AI 辅助范围、核验结果及人工修改或拒绝案例在实际发生后登记。

### 6.3 版本与变更约定

需求版本与软件版本分别管理。SRS 使用 `srs-v1.0.0` Tag/Release，软件使用 `v0.1.0`、`v0.2.0`、`v0.3.0`，Milestone 对应三个产品增量。每个发布版本关联源码、迁移、规则版本、镜像摘要、测试报告与部署说明。

新需求或基线变更先建 Issue。A 组织范围与价值确认，B/C/D 分析规则语义、接口、存储、工作量和测试影响，经人工审批更新文档、追溯矩阵与 Milestone 后实施。改变窗口、归一化或指纹语义时，提升相应语义版本并评估历史结果兼容性。

### 6.4 CI/CD 推进计划

| 触发 | 工作内容 | 放行证据与接入节点 |
| --- | --- | --- |
| 文档或仓库配置的 PR、push | Markdown 与空白检查、模块接入检测 | 基础配置已建立，变更以实际 CI 结果为准 |
| Go/Web 修改的 PR、push | Go 格式、vet、单元与竞态测试，Web 类型、测试与构建 | 随模块建立接入，检查通过并附核心覆盖声明 |
| 接口或存储变更 | 空库迁移与升级、契约核对、任务及幂等集成 | 随对应能力接入，API、前端与存储契约一致 |
| 主分支集成 | Compose 启动、健康检查、固定数据集烟测 | 从 v0.1 接入，输出预期告警并保留附件 |
| 经人工放行的版本 Tag | 构建镜像、推送、部署测试环境、烟测与 Release | 按增量发布，保存镜像摘要、部署状态及验收记录 |

具体命令遵循 `CONTRIBUTING.md` 和已落地模块。部署优先使用有权限的测试服务器或 self-hosted runner，密钥通过 GitHub Secrets 注入。部署失败恢复上一已验证镜像，数据库升级前保存一致备份，破坏性迁移经单独评审和恢复演练。

## 9. 完成定义与验收放行

### 9.1 功能与增量完成定义

功能完成需要需求与设计可追溯、实现经人工 Review、正常及异常测试通过、页面状态完整、接口权限检查有效、审计与业务一致。增量完成还需 Compose 可运行、Release 与测试版本对应、已知缺陷分级、评审和回顾形成后续任务。

每轮至少完成计划、构造、测试、评审与回顾，三次增量均保留可运行交付和证据。核心算法负责人需解释窗口、状态、证据及复杂度，其他成员需说明自己负责模块的需求、实现和验证方式。

### 9.2 v0.3 最终放行清单

- UC-01—24 按实际验收结果核对，需求、模型、设计、测试和发布之间的关联完整。
- Count、Distinct、Sequence 及 8 条规则通过金标准，正例、反例、时间边界、消费和分组隔离有测试记录。
- 相同数据集、规则与引擎版本重复分析时逻辑告警一致，处置状态、负责人和历史保持，旧规则及原始证据可追溯。
- 三角色权限、会话失效、越权拒绝和处置并发测试通过，成功业务变更与审计一致。
- 导入、任务、结果发布与进程中断的故障测试通过，失败状态和恢复方式可查询。
- 高危飞书通知、超时、重试、投递状态及重复分析场景通过，实际投递与 Mock 异常验证有记录。
- 10,000 条完整链路和 100,000 条引擎/完整链路双基准留档，报告包含环境、耗时、吞吐、内存及结果正确性。
- 干净环境部署、迁移、备份恢复、回滚和固定演示脚本可复现，发布资产与实际运行版本一致。
- D01—D10、三次增量、两次正式抽样代码评审、评审轮换、个人贡献和 AI 使用报告齐全。
- 关键缺陷关闭，遗留问题及风险由实际批准人确认，放行记录完成签字。

A/D 汇总最终验收结论，团队核对交付物、遗留缺陷和风险后完成人工放行。当前文档记录计划与验收条件，实际结果随项目执行补充。
