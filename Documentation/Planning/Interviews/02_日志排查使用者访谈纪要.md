## 一、核心问答记录

### Q1：当收到疑似攻击报警或进行事后排查时，您的标准排查流程是怎样的？

> **受访者原话**：
> “我的标准排查步骤分为四步：
>
> 1. **锚定可疑行为与时间范围**：比如收到异常流量或某 IP 频繁被投诉，先通过时间段切出日志；
> 2. **提取攻击指纹与行为特征**：看它是一直在刷同一种模式，还是在进行混合攻击。比如是单一 IP 在快速扫 404 字典，还是同一 IP 尝试了几百个不同的用户名登录 SSH；
> 3. **核实攻击是否得逞（致命判定）**：这是最关键的一步！如果是 SSH 暴力破解，扫了 500 次失败并不可怕，但如果**前面有连续失败，突然在某一行出现了 `Accepted password` 或者 `Accepted publickey`**，那意味着机器被直接打穿成了肉鸡，必须立刻拔网线应急响应！
> 4. **输出排查报告与归档**：把证据截屏、原始日志行摘录下来，提交给老师或者责任学生。”

### Q2：现有排查工具给出的告警，存在哪些让您觉得最痛苦的地方？

> **受访者原话**：
> “最痛苦的就是**‘只有结论，没有证据’**，以及**‘海量告警淹没关键威胁’**。
> 很多商业或开源 IDS 告警界面非常敷衍，就弹一条‘[High] 检测到 Web 扫描攻击’，点了详情里面只有一个源 IP 和时间，根本看不到这个 IP 到底请求了哪 50 个 URL、HTTP 响应码到底是什么，更看不到前后的关联时序。我作为分析员，根本不敢仅凭这一行字去断定它真的是攻击还是误报，最终还是得自己手动用 `grep` 去翻几十兆的日志文件核对原文。这样的工具不仅没有帮我省时间，反而增加了查证负担。
> 告警如果**不能直接把关联的所有原始日志证据行（包含行号、时间戳和脱敏原文）打包端出来**，那就是不可信的‘黑盒’。”

### Q3：对于一次告警，您需要看到哪些关键信息才敢做出处置决策？

> **受访者原话**：
> “必须有四个核心要素：
>
> 1. **规则版本与触发逻辑**：到底是哪条规则命中的？阈值是多少？统计窗口是多大？比如‘在 300 秒内不同路径 404 次数达到 20 次’；
> 2. **聚合主体（Group Key）与实际度量值**：比如源 IP 是谁、实际触发了多少次（比如阈值是 20，实际是 47 次）；
> 3. **触发事件与上下文证据链（Timeline）**：把触发该告警的关键日志行按照发生的时间顺序串联展示，每一行要有确切的原始行号和内容。比如 Sequence 场景，必须先看到前面的失败事件列表，再看到紧随其后的成功登录事件；
> 4. **处置留痕状态**：这条告警目前由谁在跟进？是新发现（open）、已认领（acknowledged）、已处置为误报（false_positive），还是已确认修复并关闭（resolved）。”

### Q4：多人共同参与排查时，如何避免同一条安全事件被多个人重复处理或互相覆盖？

> **受访者原话**：
> “实验室里平时有 3 到 4 个同学轮流值班。遇到攻防演练或突发攻击时，大家都在看系统。
> 必须有**工单化认领机制（Claim）**。未认领的告警，谁点了‘认领’，负责人就变成谁；在认领状态下，只有认领人或者管理员有权修改处置状态和写处置备注。
> 最重要的是要防止并发覆盖：比如我和另一个同学同时打开了同一条告警，他先提交了‘已解决’，我后提交了‘误报’，系统不能盲目以最后一次提交为准！必须有并发版本控制（比如返回 409 冲突），提示我页面数据已过时并刷新，确保处置决策严肃留痕。”

### Q5：发现某条规则持续产生误报时，您期望系统提供怎样的处置机制？

> **受访者原话**：
> “两方面的机制：
> 一是**告警级的人工闭环**：在告警详情页直接提供‘标记误报’按钮，强制要求输入误报理由（例如‘经核实为校内漏洞扫描实验室已授权扫描任务’），状态变成 `false_positive`。并且在以后重跑该分析任务时，**绝对不能把人工标记好的误报状态重置回未处理**！必须保持幂等。
> 二是**规则级的沙箱测试与调优**：管理员调整了规则阈值（比如把 10 次改成 30 次，或者改了正则过滤），不能直接上线影响生产环境。我希望可以在 Web 上选择一份历史数据集，在‘无副作用沙箱’里跑一下这个新规则草稿，立刻看到命中数和证据，确认没有海量误报后，再正式发布成新版本。”

## 二、提炼的用户痛点与核心诉求

1. **告警缺乏证据链导致决策成本高**：告警必须绑定不可变原始日志证据行（行号、时间戳、脱敏内容），提供可解释的上下文时间线。
2. **缺乏多事件关联检测能力**：传统工具难以识别“先暴力破解失败后突然成功”的时序复合攻击（Sequence 模式），而这类攻击往往是最高危的失陷指标。
3. **协同处置缺乏并发保护**：多人排查时存在覆盖风险，需要告警认领（Claim）流程与基于行版本/乐观锁的并发冲突（HTTP 409）防护。
4. **规则治理缺乏闭环验证手段**：直接修改规则易引发告警风暴，迫切需要无副作用的沙箱（Sandbox）回放验证功能。
5. **重跑分析时的处置状态丢失**：历史数据集重跑是常态，系统必须保证基于指纹去重，已处置的告警状态、责任人与处置备注必须保持幂等保留。

## 三、对产品设计与需求规格的输入

- **对规则引擎的输入**：
  - 必须支持三类核心检测模式：Count（频次阈值）、Distinct（基数统计，如不同 404 路径数）、Sequence（前后有序因果关联，如多次 SSH 登录失败紧随一次成功）；
  - 检测产生的 Finding 必须携带严格的不可变证据指针集合（包含触发事件引用、事件在有序数据集中的索引与行号）；
  - Sequence 检测中，`finish` 事件优先判定并消费先前的 `start` 窗口缓存，避免跨窗口误触。
- **对日志解析与导入的输入**：
  - 标准化提取事件关键属性：`event_time_us`、`source_ip`、`user`、`method`、`path`、`status` 等；
  - 建立稳定事件 ID 与数据集行号的双向映射，支撑前端点击证据行直接查看前后上下文。
- **对界面与处置流程的输入**：
  - 告警详情页展示“证据时间线（Evidence Timeline）”，按时间序排列触发事件与关联上下文；
  - 实现告警状态机：`open` → `acknowledged` → `resolved` / `false_positive`；
  - 认领与处置接口必须携带 `row_version`，并发写冲突时明确返回 HTTP 409 Conflict。
- **对权限与合规的输入**：
  - `analyst` 角色支持创建分析任务、运行规则沙箱、认领并处置告警；
  - `analyst` 无权直接发布或删除已发布规则，仅可提交草稿并在沙箱中验证。
