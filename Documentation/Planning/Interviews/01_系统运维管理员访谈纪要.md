## 一、核心问答记录

### Q1：您目前主要管理哪些类型的服务器与服务？日常会产生多大体量的日志？

> **受访者原话**：
> “我们实验室目前有 7 台常开的物理服务器和虚机，系统主要是 Ubuntu 22.04 LTS、两台 Debian 12，还有一台跑遗留实验教学平台的 CentOS 7。核心对外服务是通过 Nginx 统一做反向代理，后面挂了学生选课实验平台、代码托管 GitLab、以及几个老师的科研 Demo。
> 日志体量方面，平时 Nginx 的 `access.log` 一天大概在 30 万到 80 万行之间，文本文件大小大概 60MB 到 160MB。如果有选课或者集中提交作业，峰值能破百万行。SSH 的 `auth.log` 平时一天几万行，但一旦挂在公网或者校园网边界，天天都有扫描器在扫 22 端口，遇到暴力破解时一天能刷出 10 万到 20 万行失败记录。”

### Q2：在日常运维中，您如何判断服务器是否正在遭受攻击？当前依赖什么工具或命令进行初步排查？

> **受访者原话**：
> “日常基本上是‘被动救火’。要么是同学反映实验平台打不开了，CPU 占满了；要么是收到学校网络中心的告警邮件说我们机房某台机器在对外发包或者被当成跳板。
> 收到反馈后，我的排查手段很原始：SSH 登上去用 `tail -f`、`grep`、`awk` 和 `wc -l` 组合命令。比如查爆破，就 `grep 'Failed password' /var/log/auth.log | awk '{print $(NF-3)}' | sort | uniq -c | sort -nr | head -20`。查 Nginx 就统计前 20 个高频 IP 和 404/500 状态码。虽然我们有些机器配了 `fail2ban`，但它经常出问题：比如某个教室同一局域网的几十个同学通过同一个 NAT 教学出口访问，偶尔输错几次密码，`fail2ban` 直接把整栋楼的出口 IP 给封了半小时，学生直接炸锅投诉；而且单机封禁没有全局记录，排查起来很费劲。”

### Q3：在收集和导入日志时，您最担心或遇到过的最大麻烦是什么？

> **受访者原话**：
> “最大的麻烦有两个：**格式混乱**和**时间戳陷阱**。
> 第一是格式，不同机器的 Nginx 日志格式不完全一样，有的同学配成标准的 combined，有的加了 `$upstream_response_time`，还有的搞成了 JSON。如果我们想统一离线分析，系统如果对格式容错差，遇到一行格式不规范就直接闪退崩掉，那就完全不可用。必须能容忍脏数据，把解析不了的行挑出来，而不是整个文件报废。
> 第二是时间戳，CentOS 7 和默认 Debian 的 `auth.log` 走的是老的 RFC 3164 syslog 格式，时间长成 `Nov 19 14:20:01`，**压根没有年份，也没有时区偏移**！去年跨年（12月31日夜里到1月1日）排查一次攻击，日志排序直接倒挂，排查极其痛苦。如果要离线导入，系统必须允许我们在导入时手工指定年份和时区基准，或者做自动合理推断。”

### Q4：对于一套离线日志分析系统，您能接受的部署复杂度和机器资源开销是怎样的？

> **受访者原话**：
> “千千万万不要搞企业级那套 ELK（Elasticsearch + Logstash + Kibana）或者大型 SIEM！我们以前试过搭 ELK，好家伙，Logstash 吃内存，Elasticsearch 动不动 8GB、16GB 堆内存，几个 Java 容器跑起来，实验服务器自己的核心业务直接被 OOM 杀掉了。
> 我们极度渴望的是**单机轻量化、免运维**。最好一个 `docker-compose up -d` 几秒钟就能跑起来，静态编译，Go 写的最好，内存占用平稳在几百兆以内，最多不超过 1GB。数据库用本地 SQLite 就很合适，不需要额外部署 MySQL 集群或 Kafka，直接挂载个本地目录持久化就完事了。”

### Q5：您对系统的数据保留与清理有什么具体要求？对于重复导入同一天的日志，您期望系统如何处理？

> **受访者原话**：
> “按照网络安全法和学校审计规范，网络和登录日志至少要保留 6 个月。但实验室磁盘有限，离线分析系统导入的数据集希望是‘只读且具备独立生命周期’的。
> 关于重复导入：运维人员经常会顺手把同一批日志或者同一个文件上传两次。系统绝对不能因此产生两份混乱的告警！如果文件哈希或参数完全一样，系统应该能识别出‘已存在相同数据集’；如果重新跑相同的分析，告警和处置记录也必须保持稳定，不能重跑一次就翻倍一次告警，也不能把之前别人辛辛苦苦填的‘误报备注’给冲没了。”

## 二、提炼的用户痛点与核心诉求

1. **现有排查手段低效且缺乏可视化**：重度依赖临时 Shell 管道命令，耗时耗力，历史排查无法沉淀复盘。
2. **重型 SIEM 无法落地于轻量场景**：ELK/Wazuh 资源开销极大、学习门槛高，实验室缺乏维护大型分布式组件的人力与硬件。
3. **日志格式碎片与时间戳缺失**：Syslog RFC 3164 缺少自然年份与时区偏移，极易发生时间反序；Nginx 引号转义和脏数据容易导致传统脚本解析崩溃。
4. **单机封禁机制（如 Fail2ban）缺乏人工确认关卡**：自动硬封禁在教育网 NAT 出口极易误伤正常用户，迫切需要“离线快速检出可疑线索 + 完整证据人工处置”的安全机制。
5. **重复分析与数据一致性诉求**：重复导入或重新运行分析任务时，系统必须具备幂等性，已有处置状态绝不能丢失。

## 三、对产品设计与需求规格的输入

- **对规则引擎的输入**：
  - 核心定位于离线轻量检测，单机常驻内存控制在轻量级，避免依赖外部运行时；
  - 必须严格保证时间有序输入（按 UTC 微秒时间戳严格递增，配合行号解决同微秒排序），窗口运算 `[t-W, t]` 仅淘汰过期事件。
- **对日志解析与导入的输入**：
  - 导入前必须提供“前 100 行预览”功能，明确展示解析成功事件数与错误行；
  - 针对 SSH 传统 syslog 缺少自然年份和时区的问题，在导入界面强制要求指定 `year` 与 `timezone`（支持数值偏移如 `+08:00` 及 IANA 时区名称）；
  - 脏行容错：单行解析失败计入 `error_lines` 并安全转义保存，不中断整体文件导入。
- **对界面与处置流程的输入**：
  - 支持单机 Docker Compose 一键部署，默认挂载本地受控数据目录与 SQLite 单文件数据库；
  - 数据集进入 `ready` 状态后全量只读不可变；重复上传相同哈希及解析参数的文件直接复用。
- **对权限与合规的输入**：
  - 导入操作归属于 `admin` 权限；普通用户不可随意上传大文件破坏存储预算。
