## 一、核心问答记录

### Q1：在实验室管理或教学示范场景中，对系统权限和角色划分有哪些严格要求？

> **受访者原话**：
> “做软件工程和系统设计，最忌讳的就是‘一个超级管理员账号打天下’。必须严格落地**三角色 RBAC 隔离**：
>
> 1. `admin`（系统管理员）：负责全局配置、用户账号管理、规则发布与停用、外部通知配置。但管理员不能随意越权代替分析员下业务处置结论；
> 2. `analyst`（安全分析员）：核心业务角色，负责导入数据后的分析任务发起、沙箱验证、告警认领与人工处置；但绝对禁止直接篡改规则库版本，也不能动系统配置和用户；
> 3. `auditor`（审计合规员）：纯只读角色！教学检查人员或合规专员登录后，能查看所有已发布规则、历史版本、审计日志、分析任务和告警，但界面上所有修改按钮必须隐藏或禁用，后端接口遇到写入操作必须坚决返回 HTTP 403 拒绝。
> 同时，最后一个启用的 `admin` 必须做系统级保护，不能被自身或他人停用，避免出现系统失去管理入口的严重低级错误。”

### Q2：针对系统的关键操作，审计人员需要追踪哪些维度的元数据？如何保障证据不可篡改？

> **受访者原话**：
> “审计的灵魂在于**‘谁（Who）、在什么时间（When）、基于什么身份和入口（From Where）、对什么资源（What Object）、做了什么操作（Which Action）、产生什么版本/状态变化（Result/Diff）’**。
> 必须记入审计表的操作包括：
>
> - 认证相关：用户登录、注销、密码错误；
> - 权限相关：创建用户、角色变更、停用账户；
> - 规则治理：创建规则草稿、发布新版本（记录版本摘要与 Diff）、启停规则；
> - 业务处置：告警认领、转派（必须写明理由）、标记误报、关闭告警；
> - 外部集成：飞书通知配置的变更与重试。
> 审计数据一旦写入必须只读，且严禁在审计日志中打印用户的真实明文密码或包含真实 Secret 的 Webhook Token，敏感字段必须由系统脱敏打码。”

### Q3：针对高危或紧急安全事件，系统除界面展示外，如何与外部协同工具（如飞书）联动？

> **受访者原话**：
> “在现代运维和教学团队协同中，群机器人是非常普遍的标准实践。实验室通常建有飞书群（或企业微信群）。
> 对于高危（High）和严重（Critical）级别的新增告警，支持通过飞书自定义机器人 Webhook 发送卡片通知是极佳的加分项。
> 但设计上必须注意两点工程不变量：
>
> 1. **严禁在分析主事务中同步调用外部 HTTP**！外部飞书 API 超时或者断网，绝不能导致后端规则分析事务回滚或挂起。必须采用**发件箱（Outbox）模式**，主任务落库后，由独立的后台 Worker 异步轮询投递；
> 2. **有限重试与死信保护**：遇到网络抖动按指数退避重试（比如上限 3 次），超限后标记为 `dead` 并记录失败原因，支持管理员在后台查看投递状态并手动重试；重复分析相同数据集产生的复用告警，严禁重复触发自动外发，避免群轰炸。”

### Q4：在软件工程课程设计与期末验收场景下，您对系统如何保障开发全过程透明留痕有何建议？验收时最关注什么？

> **受访者原话**：
> “我一再强调的课程铁律是：**‘不在仓库里发生的事，视为没有发生’**。
> 期末答辩我不看花哨的 PPT 汇报，我关注三件事：
>
> 1. **资产与过程的真实性**：需求调研是不是真访谈？访谈纪要里的痛点有没有如实转化为用户故事和 SRS？有没有直接用真实未经脱敏的数据（严禁真实个人隐私和凭据泄露，必须用 RFC 5737 规范）？
> 2. **非功能质量与不变量的严肃性**：
>    - 数据集 `ready` 后的不可变性；
>    - 规则发布的语义版本不可变性；
>    - 重复分析的指纹计算与幂等性；
>    - 高并发认领时的乐观锁防覆盖（409 Conflict）；
>    - 失败任务的事务回滚原子性（staging 数据不污染正式告警表）。
> 3. **AI 工具使用的边界把关**：AI 允许且鼓励用来润色、整理和写样板代码，但架构设计、需求决断、代码 Review 必须‘人守关卡’，并在仓库里声明清楚。”

## 二、提炼的用户痛点与核心诉求

1. **粗粒度权限无法满足合规与教学考评**：缺乏三角色严格分离，缺乏只读审计员视图，难以应对实验室合规检查。
2. **规则演进缺乏严格版本快照**：规则直接修改容易导致历史分析结果无法复现，规则必须引入语义版本化且不可变。
3. **外部通知集成脆弱性**：同步调用外部接口易受网络超时拖垮主业务，亟需发件箱（Outbox）异步投递与容错设计。
4. **过程留痕与安全合规红线**：严禁泄露真实敏感信息；所有关键操作需可追溯、防篡改且受控脱敏。

## 三、对产品设计与需求规格的输入

- **对规则引擎的输入**：
  - 规则编译必须严格校验字段类型与资源预算（如窗口最大跨度、正则复杂度防 ReDoS）；
  - 任务执行绑定特定规则版本快照与特定引擎语义版本，保障历史检测 100% 可复现。
- **对日志解析与导入的输入**：
  - 样本日志入库前必须执行确定性脱敏，将公网真实 IP 映射为 RFC 5737 测试地址，用户名采用统一虚拟占位符；
  - 导入任务写入事务控制，若发生异常全流程回滚，避免半成品脏数据残留。
- **对界面与处置流程的输入**：
  - 提供 Auditor 只读视图，屏蔽一切写按钮；
  - 提供审计日志（Audit Log）专有查询界面，支持按操作者、对象类型、时间范围多维检索与 Diff 查看；
  - 针对高危告警引入 Outbox 异步投递机制，在工作台展示投递状态（pending / delivered / dead）及手动重投入口。
- **对权限与合规的输入**：
  - 严格限制最后一个 admin 账户的停用保护；
  - 用户停用或角色变更后立即强制吊销其已有全部会话（Session）。
