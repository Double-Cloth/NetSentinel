# NetSentinel 测试验收与需求追溯

版本 v0.1，状态为测试与过程交付计划。本文中的测试 ID、预期和阈值属于待实现验证项，执行结果在测试报告中按实际填写。

## 1. 质量策略与责任

先将规则语义写成可手算夹具，再分别验证独立引擎、持久化事务及 Web 工作流。B 编写引擎单元测试和慢速参考实现，A 编写解析及规则校验测试，C 编写数据库、权限和通知集成测试，D 从使用者视角编写验收测试并组织交叉执行。

每条缺陷记录需求、设计条款、复现输入、预期、实际、环境、责任人、修复 PR 与回归结果。测试失败导致调整需求或语义时通过变更 Issue 处理。所有原始输入使用授权脱敏日志或确定性合成数据，真实隐私样本不进入公开仓库。

| 层级 | 验证对象 | 产物 |
| --- | --- | --- |
| 静态检查 | Go 格式/vet、TypeScript 类型、依赖与接口一致性 | CI 检查记录 |
| 单元 | 解析、编译、谓词、分组、三类状态机、指纹 | 固定输入、预期 Finding、覆盖声明 |
| 集成 | SQLite 迁移、任务、幂等、版本、处置、审计、Outbox | API 响应、数据库断言、故障记录 |
| 端到端 | 登录、导入、规则、分析、证据、处置与只读角色 | 浏览器结果、关键截图、用例版本 |
| 性能 | 10,000 条链路、100,000 条引擎与链路 | 环境、原始数值、摘要与正确性核对 |
| 发布验收 | 干净环境、固定样本、版本、恢复与演示 | 部署日志、Release、人工放行单 |

核心引擎候选语句覆盖目标为 85%，核心分支通过显式测试清单核对，解析与事务服务候选为 80%。实际报告声明工具、范围、排除项和未覆盖原因，覆盖率与正确性夹具共同作为评审依据。

### 2.4 公共语义与配额

| ID | 场景 | 预期 |
| --- | --- | --- |
| TE-G01 | 同一内存输入连续执行两次 Run | 排序后指纹、解释、证据完全一致，耗时字段单独比较 |
| TE-G02 | 两个 Run 并发共享 CompiledRule | 状态相互独立，竞态检查通过 |
| TE-G03 | 输入时间回退、重复 event_id、event_index 不递增 | 返回 INPUT_ORDER_INVALID，调用方不发布结果 |
| TE-G04 | 缺失字段执行 neq/not_in | false，exists 按存在状态判断 |
| TE-G05 | 分组值包含分隔符、IPv4-mapped IPv6 | 编码无碰撞，IP 按统一事件语义规范化 |
| TE-G06 | 构造刚好达到和超过活跃组、缓冲、保留字符串字节、Finding、证据预算 | 达到可运行，超过显式失败，结果无静默截断 |
| TE-G07 | 执行中取消 ctx 或 sink 返回错误 | 返回对应错误并释放状态，服务清理未发布 staging |
| TE-G08 | 相同指纹对应不同 result_digest | 服务拒绝发布并报 RESULT_INCONSISTENT |
| TE-G09 | 任务间规则选择顺序不同 | 规范化规则排序后逻辑结果相同 |
| TE-G10 | 大量旧键跨越窗口后进入新键 | 过期空组可释放，预算统计包含各规则引用 |

慢速参考实现对小规模事件逐触发点重算窗口和去重集合，Sequence 显式分组并按 finish 分段。使用固定随机种子生成不同时间间隙、重复值、分组和同时间事件，将优化实现与参考实现逐项比较。期望结果由成员独立手算抽样复核，避免测试复制实现错误。

## 6. 性能基准与数据方案

### 6.1 数据组成

10,000 条链路数据建议 SSH 5,000 条与 Nginx 5,000 条，分别建立两个单来源数据集并执行兼容规则任务。100,000 条采用同构放大版，SSH 与 Nginx 各 50,000 条。引擎独立基准构造一个仅用于内存测试的混合来源数据集，统一 dataset_id、全局排序和 event_index，同时装载 8 条规则。完整链路使用两个单来源数据集、两个任务，合计执行相同 8 条规则。两种场景分别保存金标准，来源、规则指标与事件内容按映射核对，指纹在各自数据集范围比较。

数据生成器使用固定种子和 UTC 时间，记录生成器版本。基础场景混合正常事件、密集失败、404 路径枚举、失败后成功、重复路径、多个 IP/用户/主机及时间边界。原始行中单独加入忽略行与错误行时，报告原始总行数及有效事件数，性能用有效事件数作为分母。

基础 100,000 有效事件场景的输出金标准通过构造参数和参考实现核对。另设高基数、短时密集及极端输出三个压力场景，分别测试资源配额和失败行为。它们可明确触发配额超限，正常基准的数据分布须在预算内并声明时间跨度与活跃键数量。

### 6.2 测量步骤

1. 固定 Git commit、镜像摘要、规则版本、数据摘要、CPU/内存/磁盘、OS、Go/Node/SQLite 版本及配额。
2. 为引擎准备相同的预排序事件，记录读取/准备时间，引擎计时从 Run 开始至返回，包含 sink 接收成本，使用内存 sink 并单独声明。
3. 预热 1 次、正式执行 5 次，采集中位数、最慢值、峰值 RSS、分配量、活跃键、缓冲引用和输出数。
4. 完整链路从首次上传请求前开始计时，自动调用导入与分析接口直至两任务终态，包含上传、解析、排序、排队、引擎和正式提交。
5. 完整链路每轮使用隔离的新空数据库及相同文件，确保真实包含首次导入成本，重跑另做专门测量。
6. 比较每轮 Finding 指纹、reason 指标、证据与金标准，一致后再判断性能预算。
7. 输出逐轮原始数据及摘要，超预算时分析各阶段占比，优化后用相同输入重测。

SQLite 的重复上传复用行为会缩短导入时间，因此完整链路基准须重建隔离环境。重跑基准保留原库，用于比较复用数及状态保持。引擎吞吐与全链路吞吐分别计算，不混用输入准备和网络耗时口径。

## 8. 分析类与 CRC 候选

以下 18 个类属于分析模型候选，类职责可映射到多张物理表，编码时允许使用 Go struct 与服务函数组织。CRC 卡应在真人需求确认后逐一检查协作链能否完成用例。

| 类 | 核心属性/操作 | 主要职责 | 协作者 | 对应需求 |
| --- | --- | --- | --- | --- |
| User | id、role、enabled，认证/停用 | 表示账户及角色能力 | Session、AuditRecord | FR-01/02 |
| Session | token_hash、expires_at，验证/撤销 | 会话生命周期与访问上下文 | User | FR-01 |
| Dataset | digest、source、status，就绪/失败 | 不可变分析输入与统计 | SourceFile、NormalizedEvent、AnalysisTask | FR-03—06 |
| SourceFile | hash、format、storage_ref，定位行 | 保存文件身份与原文索引 | Dataset、ParseIssue、NormalizedEvent | FR-04/06 |
| NormalizedEvent | id、time、kind、fields，取字段 | 提供统一检测事件与原始引用 | SourceFile、RuleEngine、Evidence | FR-06/13/17 |
| ParseIssue | line_no、code，展示原因 | 解释无法标准化的行 | SourceFile、Dataset | FR-03/06 |
| Rule | id、enabled、draft_revision，编辑/启停 | 管理规则草稿和发布入口 | RuleVersion、AuditRecord | FR-07/10/11 |
| RuleVersion | version、spec、hash，编译 | 保存检测配置与语义版本 | Rule、RuleEngine、AnalysisTask | FR-08/10/12 |
| RuleEngine | compiled_rules，运行/统计 | 执行三类规则并产生候选命中 | NormalizedEvent、RuleVersion、Finding | FR-08/09/13 |
| WindowState | group、queue、armed，过期/加入 | 封装每规则分组的窗口状态 | RuleEngine、NormalizedEvent | FR-13/17 |
| AnalysisTask | snapshot、status、stats，领取/完成/失败 | 管理一次可复现执行 | Dataset、RuleVersion、Finding、Alert | FR-13—15/22 |
| Finding | fingerprint、reason，构建证据 | 表示引擎不可变检测结果 | RuleEngine、Evidence、Alert | FR-13/15/17 |
| Alert | status、assignee、version，认领/处置 | 保存逻辑告警和人工状态 | Finding、DispositionRecord、User | FR-16—19 |
| Evidence | event_id、ordinal、stage，追溯 | 将命中原因连接到原始事件 | Finding、NormalizedEvent、Alert | FR-17 |
| DispositionRecord | actor、action、reason，追加 | 保留人工处置历史 | Alert、User、AuditRecord | FR-18/19 |
| AuditRecord | action、object、changes，追加/查询 | 记录关键操作与结果 | User、Rule、AnalysisTask、Alert | FR-20 |
| NotificationConfig | revision、enabled、secret_ref，更新 | 管理渠道配置与加密版本 | NotificationDelivery、User | FR-21 |
| NotificationDelivery | payload、status、attempts，投递/重试 | 管理通知与尝试记录 | Alert、NotificationConfig、AuditRecord | FR-21 |

## 10. 发布、演示与放行清单

### 10.1 十二分钟演示安排

| 时间 | 操作 | 展示的工程事实 |
| --- | --- | --- |

### 10.2 v0.3 人工放行清单

- D01—D10 与实际版本对应，正式需求、设计和放行均有真人确认。
- Count、Distinct、Sequence 正反例、微秒边界、状态隔离及证据完整性通过。

- 导入、引擎、发布事务、重启与通知故障测试完成且关键缺陷关闭。
