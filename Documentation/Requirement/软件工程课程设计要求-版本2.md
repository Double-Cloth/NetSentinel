## 一、写在前面——软件工程的本质（教师的话）

这门课程设计只有一个目的：让你们把课堂上学到的模型、原则与方法，在一个真实的小项目里完整地走一遍。在动手之前，我希望你们先理解软件工程的三条本质，它们是本文件一切要求的由来。

本质一：软件开发是一个过程。从需求到部署，是可控、可追溯、可复现的工程活动，而不是灵感的堆砌。过程不是包袱，它让团队在变化发生时知道自己在哪、下一步去哪。

本质二：软件是团队协作的产物。沟通、评审、变更管理这些"软活动"，恰恰是决定项目成败的硬功夫。一个人写完所有代码，不是工程，是作业。

本质三：质量是内建于每一步的，不是最后一晚测试出来的。每一步交出的工作产品（规约、模型、代码、测试）都要经得起下一个人的使用——"创建能为他人提供价值的工作产品"。

同时，你们正处在软件工程的转折点上：AI 已经能够写代码、生成测试、整理文档。本课程不回避 AI，而是要求你们学会与 AI 协作地做工程——记住一个公式：工程 = 原型化 +规约 + 验证。AI 让原型化近乎免费，这让规约与验证比历史上任何时候都更值钱。本文件第五节的全部要求，都从这个公式出发。

## 二、项目要求

## 2.1 选题与规模

1. 团队自选具有真实业务背景的中等规模项目（校园、社区或企业场景均可，如二手交易平台、实验室预约系统、社团管理系统等），选题须经教师审核立项，避免玩具题与单表CRUD 系统；
2. 规模下限：不少于 3 个可交付增量；不少于 20 个用例（含至少 2 个非功能需求用例）；不少于 15 个分析类；至少识别并管理 1 个技术风险点；
3. 必须包含：不少于 3 种用户角色、权限控制、至少 1 个外部集成点（第三方登录、支付、地图或消息推送任选其一）。

## 2.2 过程要求（八个知识单元，缺一不可）

| 单元 | 要求 | 关键交付物 |
| --- | --- | --- |
| 1 立项与选型 | 提交项目章程，含过程模型选型论证（为何选增量/螺旋/UP/敏捷，须结合项目特点与适用场景分析） | 项目章程 |
| 2 需求调研与规约 | 真人干系人访谈（留纪要）；建立需求基线与变更管理机制，变更须走申请-评审-批准流程并留痕 | 访谈纪要、需求规约（SRS）、变更记录 |
| 3 需求建模 | 场景建模（用例图，至少 3 个细化用例及活动图）；类建模（CRC 卡与类图）；行为建模（至少 2 个关键类的状态图） | 需求分析模型包 |
| 4 设计建模 | 概要设计（体系结构、部署图、数据库、接口）；详细设计（至少 2 个核心构件）；每份规约须有一次正式评审记录 | 设计规约、评审单 |
| 5 编码与配置管理 | 全周期 Git 管理；抽样代码评审不少于 2 次 | 代码仓库、评审记录 |
| 6 迭代开发 | 至少 2 轮"计划-构造-测试-评审"迭代，每轮有迭代计划与回顾 | 迭代计划与回顾报告 |
| 7 测试 | 单元测试（核心模块覆盖率声明）+ 集成测试 + 验收测试（验收用例由客户视角成员编写） | 测试计划与报告 |
| 8 交付演示 | 可运行系统部署演示，功能与非功能各演示一项 | 部署系统、演示脚本 |

文档链必须前后可追溯：设计条目能指回需求条目，测试用例能指回需求与设计。

## 三、分组与角色要求

1. 每组 4–5 人，自由组队并报备；

| 角色 | 职责 | 对应毕业要求 |
| --- | --- | --- |
| 项目经理 | 计划、跟踪、变更与风险管理 | 11-1 |
| 需求分析师 | 调研、规约、场景建模 | 2-3 |
| 架构/设计工程师 | 概要与详细设计 | 3-1 |
| 开发工程师（≥2 人） | 编码、配置管理、单元测试 | 5-1 |
| 测试/质量工程师 | 测试设计、评审组织、缺陷跟踪 | 3-3 |

2. 增设"AI 使用负责人"（可兼任）：登记全组 AI 工具使用、维护 AI 使用报告、把关"人在关卡"记录；
3. 两轮迭代之间至少交换一次结对或评审对象；
4. 防搭便车：Git 提交按人统计 + 组内贡献度互评（0–10 分）+ 答辩随机点名。个人成绩= 小组成绩 × 贡献系数。

## 四、工程实践要求——GitHub 全流程留痕（DevOps 实践）

本课程设计要求全部工程活动在 GitHub（或教师认可的等效平台）上留痕。一条铁律：

不在仓库里发生的事，视为没有发生。

| 课设环节 | GitHub 上的落地要求 | 对应 DevOps 实践 |
| --- | --- | --- |
| 立项 | 建立仓库；README 载章程与选型论证；初始化 Projects 看板 | 持续开发 |
| 需求与变更 | 需求与变更一律建 Issue；变更走申请-评审-关闭流程 | 变更管理留痕 |
| 建模与文档 | 模型文件入库，每张图一个PR；文档目录随仓库版本化 | 文档即代码 |
| 编码 | 开启分支保护：main 分支禁止直推，一律走 Pull Request | 持续集成 |
| 评审 | 每个 PR 至少 1 人代码评审后方可合并（"人守关卡"的制度化） | 评审留痕 |
| 测试与迭代 | 配置 GitHub Actions：push 自动运行单元测试，红灯禁止合并；Milestone 对应增量 | 持续测试 |
| 部署 | Actions 自动部署（Pages/Vercel/服务器）；每个增量打 Release（v0.1/v0.2/v0.3） | 持续部署 |
| 监控（加分） | 为部署系统加访问统计或可用性监控 | 持续监控 |

提交历史将计入平时成绩：禁止"最后一晚打包上传"式的提交分布。

## 五、AI 时代的要求（本版核心）

## 5.1 五条总原则

原则一：验证而非信任。AI 的每个产出（代码、用例、文档、测试）必须有人的评审或执行级检查。责任永远不会转移给机器。

原则二：规格先行。鼓励规格驱动开发（SDD）式工作法：先写清规格，再让 AI 实现。

垃圾提示进，垃圾代码出。

原则三：人守关卡。架构决策、需求确认、合并放行三处必须由人签字；每个 AI 产出的合并请求必须有人的评审。

原则四：为再生成而设计。代码会被 AI 反复重写，真正不变的资产是规格与测试——用它们锚定行为。

原则五：护密与合规。密钥、个人数据、第三方机密严禁进入提示词；AI 生成内容须注明工具与用途。

## 5.2 传统内容与 AI 内容的分界

| 阶段 | 必须由人完成（AI 不得替代） | AI 允许且鼓励（须声明并把关） |
| --- | --- | --- |
| 立项选题 | 选型论证、风险清单 | 选题头脑风暴、竞品调研汇总 |
| 需求调研 | 真人访谈、干系人确认、需求决策 | 访谈纪要整理、用例草稿（人确认） |
| 需求建模 | 用例图/类图/状态图的语法与一致性（须能手工绘制，期末考查） | 模型一致性检查、备选场景生成 |
| 设计 | 架构决策、接口契约的签字定稿 | 候选方案对比生成、文档润色 |
| 编码 | 核心算法与关键模块（答辩须能手讲自己写的代码） | 界面、样板代码、CRUD 骨架生成（标注比例） |
| 测试 | 验收标准与放行决定 | 测试用例初稿生成、评审机器人初筛（人复核） |
| 部署运维 | 上线决定 | CI/CD 流水线、AI 辅助日志分析 |
| 文档 | 真实性声明 | 润色、翻译、格式化（声明 AI参与比例） |

## 5.3 AI 使用报告（新增交付物）

每组提交 2–3 页：使用的 AI 工具清单（如 ChatGPT、Cursor、Copilot、Spec Kit、MCP智能体等）；各阶段 AI 参与比例估计；把关方式与关卡记录（哪些 AI 产出被评审修改或拒绝，举 1–2 个真实案例）；团队对"AI 时代工程师角色"的反思。

## 5.4 学术诚信红线

AI 产出未声明、冒充个人独立完成，一经查实按学术不端处理；密钥与隐私数据进入提示词按安全事故处理。

加分项（两班统一，选做）：课程设计期间，向公开开源项目提交 PR 并被合并的，凭 PR 链接（Merged 状态）在期末答辩时申请加分——文档类 +2 分，代码类 +3 分，多项封顶 +5 分，计入过程性考核 GitHub 工程过程部分。限制条件：①目标仓库 Star 数 ≥ 100（确保有真实社区和 Maintainer）；②PR 合并到原始仓库（非自己或本组成员的 Fork）；③答辩时能口头说明 PR 的内容和提交动机（教师现场问两个问题，答不出不计分）。

评分方式：教师将借助 AI 评审计分工具读取各组仓库（提交、PR、Issue、CI 数据）自动生成证据档案与草稿分，教师复核后确定最终成绩；创新性、难度与真实理解仍以现场答辩为准。
