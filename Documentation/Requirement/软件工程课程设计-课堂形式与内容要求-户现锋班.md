## 二、总体课堂形式：讲解—研讨—点评"三段式"翻转课堂

本课程以学生分组项目为主线，课堂不是讲授知识的场所，而是检查、研讨和打磨项目的场所。每次课固定按以下节奏进行：

| 环节 | 时长(约) | 内容 |
| --- | --- | --- |
| 教师引入 | 10′ | 本次课目标、检查点标准、常见问题与案例要点（含必要的双语知识微讲授） |
| 学生讲解 | 8′×4–5组 | 每组上台讲解本阶段成果（需求/模型/设计/迭代），全员可见、计入过程成绩 |
| 点评研讨 | 20′ | 教师逐组点评＋组间互评：对照检查点找差距、给改法 |
| 布置与答疑 | 10′ | 明确课后任务、提交物与 GitHub检查点，答疑 |

三条贯穿全程的规矩（详见《要求（版本2）》）：

① GitHub 全流程留痕：需求、建模、设计、代码、测试全部以 Issue＋PR 形式推进，开启分支保护与 Actions CI——不在仓库里发生的事视为没有发生；

② AI 五总则：验证而非信任、规格先行、人守关卡、为再生成而设计、护密合规；每组设"AI使用负责人"，期末提交《AI 使用报告》；

③ 每次课都是检查点：课前提交不齐的组，取消当次讲解资格并计入过程成绩。

| 课次 | 主题 | 课堂形式 | 课内内容与流程 | 课前准备 | 课后提交物 | GitHub 检查点 |

| 第4次 · 第12周 | 项目分析建模讨论 | 教师微讲＋组间互查 | 分析建模要点微讲（类图、状态图、顺序图的语法与常见错误）；组间互查分析模型草稿；教师巡回答疑。 | 完成分析模型草稿（类/行为/数据） | 分析模型草稿（Mermaid/PlantUML 源文件入库） | models/ 目录建立＋图源文件 PR |
| 第5次 · 第13周 | 学生讲解需求分析 | 学生讲解＋教师点评 | 讲解完整分析模型：类、属性与操作、协作关系、行为；点评建模合理性与需求可追溯性。 | 完善分析模型；更新追溯矩阵 | 需求分析规约（评审签字）；分析模型定稿；追溯矩阵 v1 | 需求→用例→模型 全链路可追溯 |
| 第6次 · 第14周 | 项目设计建模讨论 · 学生讲解设计（一） | 学生讲解＋教师点评 | 讲解概要设计：体系结构风格与选型理由、数据库设计、内外接口；微讲设计概念与 AI 时代设计属性（可测试性、可演进性）。 | 完成概要设计（架构/数据库/接口） | 概要设计规约；API 契约（OpenAPI/接口文档） | 设计文档 PR＋架构决策记录 ADR |
| 第7次 · 第15周 | 学生讲解设计建模（二） | 学生讲解＋教师点评 | 讲解详细设计与关键技术方案；设计评审签字；明确编码与测试的迭代计划。 | 完成详细设计（构件级） | 详细设计规约（评审签字）；部署图；迭代计划 | Milestone 规划（迭代×2起）＋测试计划 |
| 第8次 · 第16周 | DevOps 迭代方法 · 项目规约文档要求 · 答疑 | 教师讲授＋答疑 | 讲解迭代开发与DevOps 八实践在课程项目中的落地（Issue 驱动、PR 评审、CI、里程碑、发布）；宣贯最终规约文档清单与答辩要求；AI证据包与《AI 使用报告》要求；集中答疑；布置项目验证演示要求。 | 进入编码迭代（课外 50＋40 学时） | 迭代计划确认；测试用例库初版 | Actions CI 通过＋首个可运行版本Tag |

第 16 周课后进入自主迭代期：编码（课外约50 学时）→ 测试与评审迭代（约40 学时）→ 发布与部署（约10 学时），全程 GitHub 留痕，教师与助教线上巡查仓库。

## 四、最终答辩（期末 60%）

形式：线上线下结合、固定答辩时间；每组 20 分钟＝演示 12′（功能＋非功能）＋问答 8′（每人至少回答一问，防止搭便车）。

必交完整资料链（对应大纲"按时提交完整的项目资料"）：需求调研报告 → SRS → 需求分析规约 → 概要/详细设计规约 → 测试报告 → 部署说明 →《AI 使用报告》→ 仓库链接（含 CI 状态、里程碑、贡献图）。

## 六、考核与评价

成绩构成（按教学系统配置）：过程性考核 40% ＋ 期末答辩与项目演示 60%。

| 板块 | 权重 | 构成 | 对应课程目标 |
| --- | --- | --- | --- |
| 过程性考核 | 40% | 课堂讲解与研讨表现10% ＋ 八次检查点提交20% ＋ GitHub 工程过程质量（Issue/PR/CI/里程碑）10% | 目标1–4 |
| 期末答辩与演示 | 60% | 现场功能与非功能演示20% ＋ 完整文档链 25%＋ 答辩问答 15% | 目标1–4 |

五档评价标准（沿用大纲）：

| 档位 | 总体特征 |
| --- | --- |
| 100–90 | 满勤；积极参与讨论；能正确展示项目全过程资料；文档链完整、GitHub 过程规范、AI 使用合规 |
| 89–80 | 满勤；积极参与；项目分析与设计总体正确，资料完整 |
| 79–70 | 缺勤1次；参与讨论；资料基本完整、个别环节薄弱 |
| 69–60 | 缺勤2次；较少参与；资料有明显不完整 |
| 59–0 | 缺勤≥3次；很少参与；资料大量缺陷（不及格，重修） |

一票否决（沿用《要求（版本2）》）：买卖代码/代做、伪造 GitHub 记录、AI 生成冒充人工关键决策、答辩无法解释本人负责模块——总评记不及格。

加分项（两班统一，选做）：课程设计期间，向公开开源项目提交 PR 并被合并的，凭 PR 链接（Merged 状态）在期末答辩时申请加分——文档类 +2 分，代码类 +3 分，多项封顶 +5 分，计入过程性考核 GitHub 工程过程部分。限制条件：①目标仓库 Star 数 ≥ 100（确保有真实社区和 Maintainer）；②PR 合并到原始仓库（非自己或本组成员的 Fork）；③答辩时能口头说明 PR 的内容和提交动机（教师现场问两个问题，答不出不计分）。
