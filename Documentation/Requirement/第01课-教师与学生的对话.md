# 教师与学生的对话

项目需求调研（动员与启动）· 第 9 周 · 软件工程课程设计

| 时间段 | 环节 | 时长 | 投影内容 |
| --- | --- | --- | --- |
| 0–5′ | 开场与课程定位 | 5′ | 封面 PPT（课程名+学期+教师） |

## 第一段（0–5′）开场与课程定位

### 0–1′：开场白

📢 "同学们好，从今天起我们进入软件工程课程设计。这门课和你们之前上的理论课完全不同——不是我来讲你们来听，而是你们来做我来检查。"

💡 语气定位：这是一门"动手"课，教师的角色从"讲师"变为"教练"。

### 1–3′：这门课做什么

📢 "一句话：你们要在一个学期里，组一个队、选一个题，从需求调研一路走到部署演示，做出一个能跑的软件项目。"

要点（投影课程基本信息表）：

- 8 次课（第 9–16 周），每次课都是检查点——课前交东西，课上来讲解
- 全程 GitHub 留痕——不在仓库里发生的事，视为没有发生
- 成绩：过程 40%（每次课的检查点＋讲解＋GitHub）＋ 期末答辩 60%

### 3–5′：你们的产出

📢 "到第 16 周，你们组要交出：一份需求规约、一套分析模型、一套设计文档、一个能运行的系统、一份 AI 使用报告——全部在 GitHub 上可追溯。"

💡 强调"可追溯"：每个设计决策能指回需求条目，每行代码能指回设计条目。

## 第二段（5–15′）三大本质——这门课的灵魂

📢 "在动手之前，我要你们记住三句话。这三句话贯穿整个学期，也是期末答辩时我会问你们的第一个问题。"

### 5–8′：本质一——软件开发是一个过程

- 从需求到部署，是可控、可追溯、可复现的工程活动
- 不是"灵感来了通宵写完"，而是每一步都有交付物

📢 "打个比方：这就像看病——挂号→问诊→检查→病历→处方→复诊，每步都有记录。跳过步骤的后果是什么？误诊。"

💡 对应课件：Ch8"看病"白话页。如投影增强版课件，翻到这一页让学生看图。

⚠ 考试相关：期末答辩第一个问题通常是"请描述你们的需求过程"——答不出过程说明没有走完。

### 8–11′：本质二——软件是团队协作的产物

- 沟通、评审、变更管理这些"软活动"，恰恰是决定成败的硬功夫
- 一个人写完全部代码的项目，不是团队项目，也不是软件工程

📢 "你们 4–5 人一组，每个人至少主讲一次课堂讲解、至少 10 个被合并的 PR。我会看 GitHub 的按人提交统计——别想搭便车。"

💡 对应课件：Ch8 需求工程七任务中的"协商"环节。

### 11–15′：本质三——质量是内建于每一步的

- 不是"最后一晚测试出来的"，是每一步交出的工作产品都要过评审
- 需求要评审、模型要评审、设计要评审、代码要 Review——关卡处处在

📢 "很多人以为质量是测试阶段的事。错了。到了测试阶段才发现需求理解错了，改回来的成本是设计阶段的十倍。"

💡 这就是为什么每次课都有检查点——检查点就是内建质量的关卡。

## 第三段（15–22′）GitHub 铁律与规矩

### 15–17′：铁律

📢 "这门课只有一条铁律：不在仓库里发生的事，视为没有发生。"

含义：

- 你的调研报告不在仓库里？等于没做
- 你的代码不走 PR 直接 push 到 main？分支保护会拒绝你
- 你的设计决策没有 ADR 记录？答辩时说不清"为什么这么选"

### 17–22′：具体规矩（五条）

| # | 规矩 | 怎么做 |
| --- | --- | --- |
| 1 | 分支保护 | main 分支只接受 PR 合并，禁止直接push |
| 2 | Issue 驱动 | 每件事（需求/缺陷/任务）先建Issue，再开分支做，做完 PR 关联Issue |
| 3 | PR 评审 | 每个 PR 至少一人 Review 通过才能合并——人守关卡 |
| 4 | CI 检查 | PR 提交后 Actions 自动构建测试，红了不能合并 |
| 5 | Milestone | 按迭代建 Milestone，每个 Issue 归属一个 Milestone |

💡 对应课件：Ch8 琥珀案例页"用户故事→验收标准→AI 测试"。

📢 "后面第 8 次课我会专门讲 DevOps 八实践，今天先记住这五条。"

## 第四段（22–30′）AI 五总则

📢 "最后一个规矩，也是这门课的"新东西"。你们是 AI 时代的第一批软件工程学生——AI 能写代码、生成测试、整理文档。这门课不回避 AI，但要用对。"

| # | 总则 | 一句话解释 |
| --- | --- | --- |
| 一 | 验证而非信任 | AI 的每个产出必须有人的评审或执行级检查——责任永远在人 |
| 二 | 规格先行 | 先写清规格再让 AI 实现——垃圾提示进，垃圾代码出 |
| 三 | 人守关卡 | 架构决策、需求确认、合并放行——三处必须人签字 |
| 四 | 为再生成而设计 | 代码会被反复重写，规格和测试才是锚——用它们锁定行为 |
| 五 | 护密合规 | 密钥、个人数据严禁进提示词；AI生成内容须注明 |

### 举例（27–30′）

📢 "举个例子：你们让 ChatGPT 写了一个登录模块。验证而非信任的意思是——你要逐行看它写的代码，自己跑一遍测试，确认没有安全漏洞，才允许合并。不是说"AI 写的应该没问题"。"

期末每组要交一份《AI 使用报告》：用了什么工具、用在哪些环节、哪些地方人把关。

⚠ 学术诚信红线：AI 产出未声明冒充个人完成 → 按学术不端处理；买卖代码/代做 → 一票否决。

## 第五段（30–40′）需求调研方法

📢 "规矩讲完了，现在讲怎么干活。第一步是需求调研——搞清楚"要什么"。"

### 30–33′：方法一——用户访谈

- 找到真实用户（不是自己想象的需求），面对面问 5–8 个开放性问题
- 问法示例："您现在做这件事的流程是什么？最麻烦的一步是哪里？"
- 不要问"您想要什么功能"——用户说的往往不是真正的需求

💡 比喻（课件 Ch8 沟通原则页）：顾客说"要快"，你要追问"多快算快？2G 网络 3 秒加载还是 5G 网络0.5 秒？"

### 33–35′：方法二——问卷调查

- 适合验证假设："有多少人有这个问题？"——用数据说话
- 问卷 10–15 题，5 分钟内填完；发放量 ≥ 30 份才有统计意义
- 先访谈后问卷：访谈发现痛点 → 问卷验证是否普遍

### 35–37′：方法三——工单/评论挖掘

- 去看现有系统的用户投诉、App Store 评论、客服工单
- 高频抱怨 = 高价值需求；AI 可以帮你们批量分析评论做聚类

💡 对应课件 Ch8 AI 页："LLM 从客服工单、日志与应用评论中大规模挖掘需求"。

### 37–40′：方法四——竞品分析

- 找 2–3 个同类产品，逐功能对比：有什么、缺什么、用户体验如何
- 输出一张竞品对比表（功能 × 产品），标出你们的差异化机会
- 不是抄竞品，是找竞品没解决好的问题

### 收尾（40′）

📢 "好，方法讲完了。接下来 40 分钟你们分组讨论——组队、选题、列调研计划。我在这答疑。"

💡 过渡到分组讨论环节。巡视各组，重点帮选题过大的组收窄范围。

## 附：分组讨论环节巡视要点（40′）

| 时段 | 动作 |
| --- | --- |
| 40–45′ | 各组自由组队，教师巡视确认人数（4–5人）和角色分工 |
| 45–55′ | 选题讨论：教师逐组问"一句话说清楚你的项目做什么给谁用" |
| 55–65′ | 调研计划：确认调研对象、方法、分工、时间表 |
| 65–70′ | 教师抽查 2–3 组口头汇报选题思路，全班点评 |

⚠ 巡视时最常见的三个问题：①选题太大（"智慧校园"→改为"教室预约"）；②没有真实用户（"我觉得需要"→改为去问 10 个同学）；③角色没人认领（AI 负责人最容易被忽略——强调这个角色管的是"合规"不是"技术"）。
