# 需求变更管理

适用版本：SRS v1.0.0-rc.2 及后续正式基线。执行责任账号为 Double-Cloth；账号负责人不等于教师或独立评审者。

1. 申请：使用[需求变更表单](https://github.com/Double-Cloth/NetSentinel/issues/new?template=requirement_change.yml)，登记原基线、FR/NFR、旧值、新值、来源和理由，关联 #6 与相关故事。口头意见须录入 Issue 后处理。
2. 影响分析：逐项填写用例、权限、模型、规则语义及历史结果兼容、API、存储迁移、测试、部署、工期和目标增量；不适用项说明原因。
3. 评审：真实需求负责人及受影响模块评审人给出结论、日期与证据链接；有冲突先解决，不由 AI 代签。性能和规则阈值变化必须附旧值与新验收口径。
4. 批准：批准者在关联 PR 的真实 Review 中记录批准、补正或拒绝，Issue 关联该记录。按用户 2026-11-25 最新指令，第 11 周无需教师签字，其他成员批准且合并即完成；未批准不得覆盖正式需求基线。
5. 实施：使用工作分支和 PR，同步 SRS、追溯矩阵、故事、模型、测试及版本记录。经 CI、其他成员人工 Review、讨论处理后合并。
6. 生效：PR 批准并合并后，文档任务及对应 Project 状态更新为 Done；按批准范围归档 SRS Tag/Release，记录不可变提交和资产摘要。故事仅在各自实现验收完成后更新为 Done。旧基线不得移动或覆盖；规则版本、对象 row_version 和引擎语义版本分别维护。

Project 使用现有“工作流状态”字段：Backlog → Ready → In Progress → In Review → Done。Ready 须依赖满足；产物及 CI 可审阅后进入 In Review；人工批准和合并后才进入 Done。系统自带 Status 仅辅助显示，不替代此字段。

初始基线尚未发布时，评审问题也走 Issue＋PR，记录在[评审与发布记录](评审与发布记录.md)。问题关闭、正式批准与产品验收是不同事件，不能相互替代。
